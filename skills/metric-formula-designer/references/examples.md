## 範例一：AI agent 成本（乘法鏈）

**輸入**：「公司的 AI agent 費用高，想做數據化觀測，但不確定怎麼設計指標。」

Phase 0 問出的關鍵是**用量要繼續成長、但總支出要持平**——兩個方向相反的目標並存。沒問這題會直接產出「全面砍成本」的錯誤方案。

$$\text{TOTAL SPEND} = \text{使用人數} \times \text{每人階段數} \times \text{每階段回合數} \times \text{每回合請求數} \times \text{每請求 token} \times \text{每 token 單價}$$

單位抵消：`人 × (階段/人) × (回合/階段) × (請求/回合) × (token/請求) × ($/token) = $`

**方向原則**：前兩項是採用率與參與度，應上升以反映產品價值；中間三項是 agent 在使用者請求之外自己額外做的工作，應下降；最後一項由供應商決定。

🟢 **使用人數** — 多少人在用。上升。代表採用率與覆蓋，壓它等於放棄產品價值。

🟢 **每人階段數** — 一個人開幾次。上升。代表黏著度，成長意味著產品被真正依賴。

🔴 **每階段回合數** — 一次來回幾輪。下降。理想代理應一次到位；回合數高代表理解偏差、重試或無效溝通。

🔴 **每回合請求數** — 一輪打幾次 API。下降。內部工具呼叫與子任務調度次數，過高代表路由效率不佳或冗餘查詢。

🔴 **每請求 token** — 一次送多少字。下降。精簡系統提示詞、壓縮檢索結果、啟用快取。

⚪ **每 token 單價** — 一個字多少錢。下降。任務分流（簡單任務走輕量模型）、批次折扣、議價。

**副作用**：每請求 token 與每階段回合數互相推擠——上下文砍太兇，agent 缺資訊就多跑幾輪，總量不降反升。這兩項必須綁在一起看，單看其中一項的改善報告沒有意義。

**這個範例的重點不是這條公式，是 Phase 0 問出了「兩個相反方向並存」。** 跳過反問的話產出會是六項全部要求下降，那會砍掉產品的採用率。

## 範例二：開發速度變慢（離散度分解）

**輸入**：「身為 PM 我發現工程師的開發速度慢下來，但缺少具體的數值化證據，不確定該往哪些方向改善。」

Phase 0 答案：三個症狀都有、**估不準最痛**；資料只有 git commit 時間；護欄是品質與技術債。

**Phase 1 選了三層疊加的算子。** 「估不準」的標的量是離散程度不是平均值，所以主算子是離散度分解；另外用 Little's Law 當恆等式解釋為什麼三個症狀同時出現：

$$\text{平均前置時間} = \frac{\text{平均在製品數}}{\text{平均吞吐量}}$$

三個症狀是同一件事的三種投影。在製品上升、吞吐量持平，前置時間必然變長，而高利用率下變異惡化得更快——所以「估不準最痛」是排隊系統被推到滿載的標準病徵。

底層乘法鏈（四項全部只靠 git 可算）：

$$\text{分支存活時間} = \text{淨變更規模} \times \text{重工倍數} \times \text{單位實作耗時} \times \text{阻塞倍數}$$

`淨行數 × (總觸碰行數/淨行數) × (活躍小時/總觸碰行數) × (存活小時/活躍小時) = 存活小時`

🔴 **阻塞倍數**（存活小時 ÷ 活躍小時）— 下降。流動效率的倒數，典型值 6 到 20，代表一張票的生命裡只有 5%~15% 真的有人在動它。它是前置時間與變異的共同放大器，而且降它不需要任何人寫得更快。

🔴 **淨變更規模** — 下降。批量大小同時放大 review 時間、衝突機率與回溯成本，而且是變異的主要來源，所以縮小批量是直接對著「估不準」下手。

🔴 **合併前重工倍數** — 下降。寫了又改掉的比例，是「開工前資訊不足」的量化證據，改善手段在 PM 側。

🟡 **單位實作耗時** — 不設方向，只做監控。唯一直接對應「工程師寫得快不快」的一項，也是唯一壓下去會同時傷害兩個護欄的一項（寫快的最直接手段就是少寫測試）。當它下降而重工率上升，代表團隊在偷工。

🟢 **合併後回流率**（品質）、**熱點集中度與測試佔比**（技術債）— 上升即警示。

**副作用**：縮小批量若 review 容量不變，每個分支等待反而變長，批量降 50% 而阻塞倍數升 2 倍等於白做。另外看到「85% 時間沒人動」的直覺反應是多開分支填滿空檔——那會提高在製品，依 Little's Law 前置時間直接上升。正確方向恰好相反。

**充分條件代理**：git 裡沒有估計值，估不準無法直接量測。改用 P85/P50 的分支存活時間比值——比值大到某個程度，任何估計方法都不可能準。這在數學上足以證明估不準，而且把問題從「人不用心」轉成「系統不允許」。

**最大的落地風險是 squash merge**：主幹上只剩一個 commit，首 commit 時間與重工資訊全部消失，這套的一半就報廢。要在寫任何程式碼之前先確認。

## 範例三：訂閱數不成長（存量流量）

**輸入**：「付費訂閱數這半年幾乎沒動，但行銷一直說流量有進來。」

存量問題不要拆成乘法鏈。先寫流量方程：

$$\text{期末訂閱數} = \text{期初訂閱數} + \text{新增} + \text{回流} - \text{流失}$$

「總數沒動」在這個式子裡有兩種完全不同的成因：新增小（漏斗前段壞了），或新增大但流失同樣大（漏桶）。這兩者的改善方向相反，**先算出流入流出的絕對值再往下拆**，否則會把行銷預算加在漏桶上。

流入流出各自再拆，這一層才用乘法鏈：

```
新增 = 造訪數 × 註冊率 × 試用啟用率 × 付費轉換率
流失 = 期初訂閱數 × 流失率
```

流失率再往下做**加法分解**（這裡才用 MECE）：主動取消 + 付款失敗 + 降級。三者互斥且窮盡，而付款失敗通常是三者中最容易改、也最常被誤算進「產品不夠好」的一項。

🟢 造訪數 — 上升。🔴 註冊率、啟用率、轉換率、付款失敗率 — 下降或上升視分子而定。🟡 主動取消率 — 壓它不能靠增加取消難度。

**這個範例的重點**：直接跳到「轉換率漏斗」會漏掉流失那一側，而總數不動時，流失側往往才是主因。存量問題一律先寫流量方程再拆漏斗。
