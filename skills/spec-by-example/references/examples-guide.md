## 1. 完整 Spec 文件結構

一份 spec 依序包含以下區塊。前半段（背景 → Given-When-Then）建立「大家對**要做什麼**的共識」；後半段（Implementation → Further Notes）記錄「已拍板的**決策與邊界**」。

| 區塊 | 目的 | 誰最在意 |
|---|---|---|
| 功能背景 | 一句話講清楚角色、目的、價值 | PO |
| Problem Statement | 使用者現在遇到什麼問題 | PO |
| Solution | 這功能怎麼解決 | PO |
| User Stories | 窮舉各角色／狀態的需求 | PO / Dev |
| 業務規則 | Examples 的依據 | PO / Dev |
| Examples 表格 | 具體情境（核心）| 三方 |
| Given-When-Then | 關鍵情境的 BDD 表述 | 三方 |
| Implementation Decisions | 已拍板的技術決策 | Dev |
| Testing Decisions | 怎麼測、在哪個 seam 測 | Dev / QA |
| Out of Scope | 明確排除項 | 三方 |
| Open Questions | 待確認問題 | 三方 |
| Further Notes | 其他補充 | — |

## 2. 各區塊撰寫指南

### 2.1 功能背景

用固定四行點出角色、目的、價值,讓讀者三秒進入狀況:

```
功能：[功能名稱]
作為：[角色]
我想要：[目的]
以便於：[業務價值]
```

### 2.2 Problem Statement 與 Solution

兩段都**從使用者視角**寫,不要跳進實作。

- **Problem Statement**：現況造成什麼痛（誰痛、痛在哪、代價是什麼）。
- **Solution**：使用者會看到／操作到什麼改變,而不是「我們會用 Redis 存⋯」。技術怎麼做留給 Implementation Decisions。

範例（折扣功能）:
- **Problem**：結帳頁沒有輸入折扣碼的地方,行銷發出的優惠碼無處可用,使用者流失。
- **Solution**：結帳頁新增折扣碼欄位;輸入有效碼即時反映折抵後金額。

### 2.3 User Stories

一份**很長**的編號清單,格式:

```
作為 <角色>，我想要 <功能>，以便於 <好處>
```

要點:
- **窮舉**,不是三五條交差。橫向掃過不同角色（終端使用者、上游服務、維運、客服⋯）,縱向掃過不同狀態（正常、邊界、失敗、併發、過期⋯）。
- 一條只講一件事;好處要是「使用者真正在意的結果」,不是複述功能。

範例（部分）:
1. 作為行動銀行客戶,我想要看到各帳戶餘額,以便於做更明智的消費決策。
2. 作為行動銀行客戶,我想要在餘額不足時被清楚擋下,以便於不會透支產生費用。

### 2.4 業務規則

條列規則。**每條規則都應該對應到 Examples 裡至少一列**——規則是 Examples 的來源,兩者要對得起來。

範例（ATM 提款）:
1. 提款金額不得超過餘額。
2. 帳戶凍結時不允許提款。
3. 單日提款上限 20,000。
4. 提款金額須為 1,000 的倍數。

### 2.5 Examples 表格（核心）

把規則變成具體情境。**必須同時覆蓋 Happy／Edge／Negative**,並在備註標明類型。

**基本格式（三欄）**

| 條件（Given） | 操作（When） | 預期結果（Then） |
|---|---|---|
| 具體前置狀態 | 使用者動作 | 系統結果 |

**進階格式（多欄條件）** — 條件多時展開成多欄,一列一情境:

| 帳戶狀態 | 餘額 | 操作 | 預期結果 | 備註 |
|---|---|---|---|---|
| 正常 | 1000 | 提款 500 | 成功,餘額 500 | Happy |
| 正常 | 1000 | 提款 1000 | 成功,餘額 0 | Edge：剛好領完 |
| 正常 | 1000 | 提款 1001 | 失敗：餘額不足 | Negative |
| 凍結 | 1000 | 提款 500 | 失敗：帳戶已凍結 | Negative |

**組合維度範例（權限控管）** — 角色 × 操作 × 狀態,把 negative（403／404／重導）攤開:

| 角色 | 操作 | 文章狀態 | 預期結果 |
|---|---|---|---|
| Editor | 編輯 | 自己的文章 | 允許 |
| Editor | 編輯 | 他人的文章 | 拒絕：403 |
| Viewer | 讀取 | 草稿 | 拒絕：404 |
| 未登入 | 任意 | 任意 | 重導登入頁 |

### 2.6 Given-When-Then

從 Examples 挑「關鍵／容易誤解」的情境轉成 Gherkin（不用每列都轉）。語言與使用者一致。

**基本結構**

```gherkin
Scenario: [清楚描述情境]
  Given [初始狀態]
  And   [額外前置]（可選）
  When  [操作]
  Then  [結果]
  And   [額外驗證]（可選）
```

**Scenario Outline（多筆資料共用同一情境）**

```gherkin
Scenario Outline: 依折扣碼計算結帳金額
  Given 購物車金額為 <原始金額>
  And   輸入折扣碼 <折扣碼>
  When  點擊「確認結帳」
  Then  最終應付金額應為 <最終金額>

  Examples:
    | 原始金額 | 折扣碼     | 最終金額 |
    | 1000    | SAVE10    | 900     |
    | 1000    | SAVE50PCT | 500     |
    | 200     | SAVE300   | 0（不為負）|
```

### 2.7 Implementation Decisions

記錄**已拍板的技術決策**,讓 Dev 有共識。可包含:會新增／修改的模組、介面形狀、schema 變更、API 合約、關鍵互動、開發者的技術澄清、架構決策。

- **不要寫具體檔案路徑或程式碼片段**——它們很快過時,寫「決策」而非「實作」。
- **例外**：若原型（prototype）產出一段比文字更精確表達某決策的片段（狀態機、reducer、schema、type 形狀）,可內嵌並註明「來自原型」,但只留決策密度高的關鍵部分,不是可跑的 demo。範例見第 4 節的 `IdempotencyRecord`。

### 2.8 Testing Decisions 與測試接縫（Seams）

描述「**怎麼測**」,不是寫測試。包含三件事:

1. **好測試的定義** — 只驗**外部可觀察的行為**（狀態碼、回傳內容、可觀察的副作用）,不綁實作細節（內部欄位命名、私有函式）。實作重構時,測試不該跟著壞。
2. **測試接縫（seams）** — 寫下「測試從哪個介面打進去、從哪裡觀察」,並簡述為何選這個接縫。接縫的原則、好處與取捨(沿用既有、用最高、越少越好、與使用者確認)詳見 SKILL.md 的〈測試接縫（Seams）〉一節。
3. **Prior art** — codebase 裡類似的既有測試,照它的風格寫。

### 2.9 Out of Scope

明確列出這份 spec **不**涵蓋的東西,避免範圍蔓延與誤解。寧可多寫一條,把「看起來相關但這次不做」的講清楚。

### 2.10 Open Questions

所有待釐清的問題都列出,標清楚類型與負責人:

| # | 問題 | 類型 | 負責確認 | 狀態 |
|---|---|---|---|---|
| 1 | [業務問題] | 業務規則 | PO | ⬜ 待確認 |
| 2 | [技術限制] | 技術約束 | Dev | ⬜ 待確認 |
| 3 | [測試疑慮] | 測試覆蓋 | QA | ⬜ 待確認 |

類型參考:**業務規則**（政策／流程／例外）、**技術約束**（系統限制／效能／整合）、**測試覆蓋**（難自動化／需手動驗證）、**UI/UX**（介面行為／錯誤文案）。

### 2.11 Further Notes

放不屬於上述任何區塊、但對讀者有幫助的補充:未來延伸方向、已知風險、相依項目、命名／邊界的小提醒等。

## 3. 常見 Edge Case 清單（三角色審視）

戴上 QA 帽子時,逐項檢查是否已被 Examples 覆蓋:

### 數值邊界
- [ ] 最大值（如餘額剛好等於提款金額）
- [ ] 最小值（如金額為 0）
- [ ] 超出上限（如比上限多 1）
- [ ] 負數輸入

### 狀態邊界
- [ ] 資源剛好被其他操作佔用
- [ ] 過渡狀態（如剛好到期）
- [ ] 空值 / 未初始化

### 權限邊界
- [ ] 未登入
- [ ] 已登入但無權限
- [ ] 僅有部分權限（只能操作自己的資源）

### 時間相關
- [ ] 到期臨界點（如今天最後一秒）
- [ ] 跨日 / 跨月 / 跨年計算

### 重複與併發
- [ ] 重複提交（double submit）
- [ ] 相同操作連續／併發執行

## 4. 完整範例 A：冪等訂單提交 API（後端）

> 示範「融合後」的完整 spec:從 Problem Statement 到 Further Notes 的所有區塊如何一起填寫,情境取自後端／資料工程。

#### 功能背景

```
功能：訂單提交 API 支援冪等鍵（Idempotency-Key）
作為：呼叫下單 API 的前端／上游服務
我想要：帶著冪等鍵重試同一筆下單請求
以便於：在網路逾時或重試時,不會意外建立重複訂單
```

#### Problem Statement

下單請求在網路逾時後,客戶端常會自動重試。目前每次 `POST /orders` 都會建立一筆新訂單,導致使用者被重複扣款、後台出現重複訂單,客服處理成本高。

#### Solution

客戶端可在請求標頭帶上 `Idempotency-Key`。同一把鍵在有效期內重送,伺服器回傳「第一次」的結果,而不是再建立一筆訂單;不同鍵則視為不同請求。

#### User Stories

1. 作為上游服務,我想要為每次下單產生一把冪等鍵,以便於逾時重試時不會重複建單。
2. 作為上游服務,我想要在重試時拿回第一次的訂單結果（含 order_id）,以便於後續流程接得起來。
3. 作為上游服務,我想要在「請求內容不同、鍵卻相同」時得到明確錯誤,以便於及早發現用鍵錯誤。
4. 作為維運,我想要冪等記錄有明確保存期限,以便於儲存空間不會無限膨脹。
5. 作為維運,我想要下游（如金流）失敗時冪等鍵不要卡住,以便於故障可自我恢復。
6. 作為前端,我想要併發送出兩次相同鍵時最終只成立一筆訂單,以便於使用者連點也安全。

（實際清單應繼續窮舉:不同租戶、鍵過長、store 暫時不可用等。）

#### 業務規則

1. 帶相同 `Idempotency-Key` 且「請求內容相同」→ 回傳首次結果,不重複建單。
2. 冪等鍵有效期為 24 小時;過期後同一把鍵視為全新請求。
3. 相同鍵但「請求內容不同」→ 回 422,拒絕處理。
4. 冪等鍵的作用範圍限單一 API 端點與單一租戶（tenant）。
5. 首次請求「處理中」時,第二個相同鍵的併發請求需等待或收到「處理中」狀態,不得平行建單。

#### Examples 表格

| 冪等鍵 | 鍵狀態 | 本次請求內容 | 操作 | 預期結果 | 備註 |
|---|---|---|---|---|---|
| 無 | — | 有效 | POST /orders | 建立新訂單,回 201 | Happy（未用冪等）|
| K1 | 未使用 | 有效 | POST /orders | 建立新訂單,回 201,記錄 K1→結果 | Happy |
| K1 | 已完成 | 與首次相同 | 重送 | 回首次結果（同 order_id）,回 200,不建單 | 冪等命中 |
| K1 | 已完成 | 與首次不同 | 重送 | 回 422：鍵與內容不符 | Negative |
| K1 | 已過期(>24h) | 有效 | 重送 | 視為新請求,建立新訂單 | Edge：到期臨界 |
| K1 | 處理中 | 與首次相同 | 併發重送 | 回 409／處理中,不平行建單 | Edge：併發 |
| K1 | 首次下游失敗 | 有效 | 重送 | 允許重新處理,不永久卡死 | Edge：故障恢復 |

#### Given-When-Then

```gherkin
Scenario: 相同冪等鍵、相同內容重送回傳首次結果
  Given 已用鍵 "K1" 成功建立訂單 order_id=1001
  When  以相同鍵 "K1" 與相同內容再次送出 POST /orders
  Then  回傳 HTTP 200
  And   回傳的 order_id 仍為 1001
  And   系統未建立第二筆訂單

Scenario: 相同鍵但內容不同
  Given 已用鍵 "K1" 建立過訂單
  When  以鍵 "K1" 送出「內容不同」的 POST /orders
  Then  回傳 HTTP 422
  And   錯誤訊息指出冪等鍵與請求內容不符
```

#### Implementation Decisions

- 於 API gateway／handler 層（最外層）攔截 `Idempotency-Key`,在進入下單領域邏輯前完成冪等判斷。
- 冪等記錄存於獨立的 idempotency store,以 (tenant_id, endpoint, key) 為主鍵;請求內容以雜湊比對是否相同。
- 併發控制:以「先寫入一筆 in-progress 記錄」搶佔（唯一鍵約束）,搶輸者讀既有記錄。
- 過期以記錄的 created_at + 24h 判定;清理由 store 的 TTL 機制負責。
- 下游失敗時,將記錄標記為 failed 而非 completed,允許同鍵重試。

> 以下 schema 來自原型,比文字更精確地表達冪等記錄的形狀（僅保留關鍵欄位）:

```go
type IdempotencyRecord struct {
    Key         string    // 與 TenantID, Endpoint 共同構成唯一鍵
    TenantID    string
    Endpoint    string
    RequestHash string    // 比對請求內容是否相同
    Status      string    // in_progress | completed | failed
    Response    []byte    // completed 時的首次回應快照
    CreatedAt   time.Time // + 24h 為過期時點
}
```

#### Testing Decisions

- 好測試:只驗證對外可觀察的行為——同鍵重送的 HTTP 狀態碼、回應內容、以及「訂單筆數」是否符合預期;不驗 store 的內部欄位命名或實作細節。
- 測試接縫（seam）:在 HTTP 端點層打進去（送真實 `POST /orders`）,這是最高、最貼近使用者行為的接縫;不為冪等邏輯另開內部 seam。
- 要覆蓋的模組:下單 handler 的冪等中介層。
- Prior art:可參考現有 `payments` 端點的重試／去重整合測試寫法。

#### Out of Scope

- 冪等鍵的產生策略（由客戶端負責）。
- 跨端點共用同一把鍵的語意。
- 金流本身的對帳與退款流程。

#### Open Questions

| # | 問題 | 類型 | 負責確認 | 狀態 |
|---|---|---|---|---|
| 1 | 有效期 24h 是否符合業務需求? | 業務規則 | PO | ⬜ 待確認 |
| 2 | 「處理中」併發時要回 409 還是等待重試? | 技術約束 | Dev | ⬜ 待確認 |
| 3 | 併發搶佔的競態如何穩定測試? | 測試覆蓋 | QA | ⬜ 待確認 |

#### Further Notes

- 冪等鍵長度與字元集需另定義（避免超長鍵撐爆索引）。
- 若未來多端點需要冪等,考慮把中介層抽為共用套件。

## 5. 完整範例 B：ATM 提款（金融）

> 較單純的領域,同樣填滿所有區塊,示範融合結構不綁特定情境。

#### 功能背景

```
功能：ATM 提款
作為：銀行帳戶持有人
我想要：從 ATM 提取現金
以便於：在需要時取得現金
```

#### Problem Statement

ATM 目前允許任意金額提款,常因面額限制吐鈔失敗、或讓使用者一次領超過風控上限,增加現金調度與盜刷損失風險。

#### Solution

提款時系統即時檢核餘額、單日上限、面額倍數與帳戶狀態,只放行合法金額,並在被擋下時給明確原因。

#### User Stories

1. 作為帳戶持有人,我想要領出不超過餘額的金額,以便於不會透支。
2. 作為帳戶持有人,我想要在超過單日上限時被清楚擋下,以便於知道還能領多少。
3. 作為帳戶持有人,我想要輸入非面額倍數時被提醒,以便於重新輸入正確金額。
4. 作為風控,我想要凍結帳戶完全無法提款,以便於阻止盜領。
5. 作為維運,我想要單日已提金額能跨交易累計,以便於上限判斷正確。

#### 業務規則

1. 提款金額不得超過餘額。
2. 帳戶凍結時不允許提款。
3. 單日提款上限 20,000。
4. 提款金額須為 1,000 的倍數。

#### Examples 表格

| 帳戶狀態 | 餘額 | 今日已提 | 提款金額 | 預期結果 | 備註 |
|---|---|---|---|---|---|
| 正常 | 5000 | 0 | 3000 | 成功,餘額 2000 | Happy |
| 正常 | 5000 | 0 | 5000 | 成功,餘額 0 | Edge：領完 |
| 正常 | 5000 | 0 | 6000 | 失敗：餘額不足 | Negative |
| 正常 | 50000 | 0 | 25000 | 失敗：超過單日上限 | Negative |
| 正常 | 50000 | 15000 | 6000 | 失敗：超過單日上限 | Edge：累計 |
| 正常 | 50000 | 15000 | 5000 | 成功 | Edge：剛好到上限 |
| 正常 | 5000 | 0 | 1500 | 失敗：非 1000 倍數 | Negative |
| 凍結 | 5000 | 0 | 1000 | 失敗：帳戶已凍結 | Negative |

#### Given-When-Then

```gherkin
Scenario: 提款超過單日上限
  Given 帳戶狀態為正常
  And   帳戶餘額為 50000 元
  And   今日已提款 15000 元
  When  使用者提款 6000 元
  Then  交易失敗
  And   顯示「已超過單日提款上限 20000 元」
  And   帳戶餘額不變
```

#### Implementation Decisions

- 檢核順序在提款服務層集中處理:帳戶狀態 → 面額倍數 → 餘額 → 單日上限,任一不過即回對應錯誤。
- 單日已提金額以「當日累計」查詢,跨交易累加;日界以帳戶所在時區的 00:00 為準。
- 扣款與當日累計需在同一交易中原子完成,避免併發下超領。

#### Testing Decisions

- 好測試:驗提款 API 的成功／失敗結果、錯誤原因、餘額與當日累計的變化;不驗內部檢核函式的呼叫順序。
- 測試接縫:在提款服務的對外入口打進去（帶帳戶狀態、餘額、當日已提的前置）,涵蓋上表各列。
- Prior art:參考現有 `transfer`（轉帳）服務的餘額／上限檢核測試。

#### Out of Scope

- 實體 ATM 吐鈔硬體與清機流程。
- 跨行提款手續費計算。
- 提款以外的交易（存款、轉帳）。
