# Specification by Example Skill

在動工實作前，把抽象需求轉化為「具體、可執行的範例」，並整理成一份人類可讀、可討論的規格文件，讓開發、測試、產品基於相同理解協作。這份 spec 的目的是講清楚「要做什麼、如何驗證」——不是寫測試程式碼，也不是實作。

---

## 核心理念：具體範例 > 抽象規格

一句抽象敘述可以有十種解讀；一個具體範例只有一種。範例同時是「規格」與「未來測試的種子」。

| ❌ 抽象規格（避免） | ✅ 具體範例（目標） |
|---|---|
| 系統應該快速回應 | 使用者點擊送出後，頁面在 2 秒內完成導向 |
| 使用者可以提款 | 帳戶餘額 1000、提款 500 → 成功，餘額變 500 |
| 登入功能應該安全 | 連續輸入錯誤密碼 5 次後，帳戶鎖定 15 分鐘 |

---

## 前提：先理解脈絡，再寫範例

若在**既有程式碼庫**中作業，動筆前先：

- **探索程式碼**，理解目前狀態，別把 spec 建立在錯誤假設上。
- **沿用專案的領域詞彙（domain glossary）**，整份 spec 用同一套用語，避免同義詞造成誤解。
- **尊重你要動到區域既有的 ADR（架構決策紀錄）**，不要在 spec 裡默默推翻既有決策。

若是全新專案，跳過上述，直接從理解需求開始。

---

## Agent 角色扮演：一人分飾三角

撰寫時同時用三種視角審視。只戴一頂帽子，很容易只覆蓋 happy path：

**🎯 Product Owner（PO）視角** — 業務目標是什麼？核心 happy path 有哪些？使用者真正的意圖與價值？

**🛠️ Developer（Dev）視角** — 邊界條件在哪？有哪些技術限制、前置狀態、併發或失敗模式要體現？資料的前置條件是什麼？

**🔍 QA Tester 視角** — 哪些 edge cases 容易被遺漏？哪些 negative／失敗情境需要覆蓋？哪些「組合」情境有風險？

---

## 流程

1. **理解脈絡與需求（Discovery）** — （既有專案）探索程式碼、確認領域詞彙與 ADR；識別主要角色（Actor）與業務目標。需求模糊時，先問清楚核心業務場景再動筆，一次聚焦一個重點。

2. **三角色審視需求** — 分別戴上 PO／Dev／QA 帽子，把 happy path、邊界條件、edge cases、negative 情境都攤開。

3. **產出具體範例（Specification）** — 從業務規則推導 Examples 表格（Happy／Edge／Negative 都要有），再把關鍵情境轉成 Given-When-Then。

4. **規劃測試接縫（Seams）並與使用者確認** — 決定要在哪個介面驗證這個功能（見〈測試接縫〉）。**先確認接縫是否符合使用者預期，再往下寫決策**——接縫選錯，後面的測試決策都會歪掉。

5. **記錄實作與測試決策** — 把已拍板的模組、介面、schema、API 合約，以及測試範圍與 prior art，寫進 Implementation／Testing Decisions。

6. **列出 Open Questions** — 所有還不確定、需要 PO／Dev／QA 拍板的問題，都明確標記為「待確認」。

7. **邀請精煉（Refinement）** — 結尾詢問使用者範例是否符合預期、還有哪些情境要補；依回饋持續迭代。

## 規格文件模板

依此結構與順序產出（各區塊視情境增減，但命名與順序維持一致）：

```markdown
# [功能名稱]
## 功能背景                  — 功能 / 作為 / 我想要 / 以便於
## Problem Statement         — 使用者視角的問題
## Solution                  — 使用者視角的解法
## User Stories              — 長清單：作為 <角色>，我想要 <功能>，以便於 <好處>
## 業務規則                  — Examples 的依據
## Examples 表格             — 核心：Happy / Edge / Negative
## Given-When-Then           — 關鍵情境轉 Gherkin
## Implementation Decisions  — 模組 / 介面 / schema / API 合約（不含檔案路徑與程式碼）
## Testing Decisions         — 測什麼、在哪個 seam 測、prior art（不含測試碼）
## Out of Scope              — 明確排除項
## Open Questions            — 待確認問題表
## Further Notes             — 其他補充
```

## 各區塊撰寫要點

- **User Stories 要「長」**：盡量窮舉，涵蓋不同角色、不同權限、不同狀態下的需求，不是三五條交差。每條都要有明確的 `<角色>` / `<功能>` / `<好處>`。

- **Examples 三類都要有**：Happy Path（正常流程）、Edge Cases（邊界，如剛好等於上限、值為 0、超過 1）、Negative Scenarios（失敗，如權限不足、狀態不允許）。缺任何一類，都代表審視還不完整。

- **Implementation Decisions 不放程式碼與檔案路徑**：它們很快過時，改記「決策」本身——要動哪些模組、介面長怎樣、schema／API 合約怎麼變、關鍵互動。**例外**：若原型（prototype）產出一段比文字更精確表達某決策的片段（狀態機、reducer、schema、type 形狀），可內嵌並註明來自原型，但只留「決策密度高」的關鍵部分，不是可跑的 demo。

- **Testing Decisions 只描述「怎麼測」，不寫測試**：說明好測試只驗**外部行為**、不綁實作細節；列出要測的模組、選定的測試接縫（seams），以及程式碼庫中類似的既有測試（prior art）。不要寫實際測試碼或 step definitions——那是 Dev 的工作。

- **Open Questions 標清楚類型與負責人**：業務規則 → PO、技術約束 → Dev、測試覆蓋 → QA。

## 測試接縫（Seams）

這是整份 spec 中**最影響測試長期成本**的一段,值得想清楚再寫。

### 什麼是接縫

「接縫（seam）」是你能夠改變程式行為、卻不必動到那段程式本身的地方——在測試語境下,就是**測試從哪個介面把輸入打進去、從哪裡觀察結果**。一個功能的接縫,就是它對外的「前門」。

### 為什麼重要（好處）

- **測試能撐過重構**——這是最大的回報。接縫定在對外行為上,測試釘住的是「契約」而非「結構」;只要對外行為不變,內部隨你重寫,測試都不該壞。反過來,接縫定太低(私有函式、內部型別),重構就會弄壞一堆其實行為沒變的測試,製造假警報。
- **更少的替身與設定**——越高的接縫,要 mock 的協作對象越少、前置越單純,測試更好寫也更好維護。
- **更貼近真實、每個測試更有價值**——高接縫測到的東西接近呼叫端/使用者真正經歷的路徑,能抓到整合問題,同樣數量的測試給更多信心。
- **一個清楚的入口**——每個功能一個接縫,新人一眼知道該從哪裡測,也不會出現重複、彼此打架的覆蓋。
- **反過來磨利 Examples**——先決定接縫會逼你講清楚「這個功能對外可觀察的行為是什麼」,連帶讓 Examples 更精準。

### 原則（附理由）

- **優先沿用既有接縫,不要新開。** 每多一個接縫,就多一塊要維護的表面、多一處內部細節外洩到測試。沿用能讓整體測試拓撲維持小而穩。
- **用「最高」的接縫。** 「高」= 越靠近呼叫端/使用者、越遠離實作細節。接縫越高,保留的實作自由度越大、測試越真實。
- **接縫越少越好,理想上整個 codebase 一個。** 每個接縫都是一份你必須維持穩定的契約;接縫越多,脆弱的契約越多、重疊的測試越多、維護越貴。
- **需要新接縫時,在你能做到的最高點提出。** 別為了方便就往低處鑽。

### 怎麼挑

讓「對外可觀察的行為」替你選接縫:接縫就是 Examples 的 Given／When／Then 能被觀察到的那個介面。若 Examples 講的是「`POST /orders` → 201、建立訂單」,HTTP 端點就是天然的接縫。

後端／資料工程常見的高接縫:HTTP handler／端點、訊息或佇列的消費入口、CLI 指令、對外的 package API、一個 service／use-case 的最外層邊界。要避免的低接縫:私有函式、repository 內部、特定 SQL、struct 欄位名。

### 取捨

「最高」不是教條,而是有上界的:接縫拉太高(整條 e2e、打真實 DB／網路)會變慢、變 flaky。實務上取的是「**在測試仍穩定、速度仍可接受的前提下,最高的那個接縫**」。若最高接縫太慢,退一階到剛好能觀察到目標行為、又不綁實作的地方,並把這個取捨寫進 Testing Decisions。

### 確認關卡

**記錄接縫後,先與使用者確認是否符合預期,再往下寫實作與測試決策。** 接縫選錯,後面的測試決策會整串歪掉,所以這是一個明確的停下來對齊的點。

---

## 注意事項

- **不寫測試程式碼或 step definitions**——這份 spec 是給人讀、給人討論的，實作測試是 Dev 的工作。
- **不討論自動化工具**（Cucumber、SpecFlow、Behave 等）——聚焦在情境本身，不是工具選型。
- **範例要能獨立閱讀**——不需要額外口頭解釋，就看得懂條件、操作、結果。
- **語言與使用者一致**（中文／英文），整份 spec 用同一套領域詞彙。
- 這是「動工前」的產物：目標是讓大家對「要做什麼、如何驗證」達成共識，不是產出實作。
