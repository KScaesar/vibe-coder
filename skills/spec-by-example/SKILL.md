# Specification by Example

> **核心**：整理成一份人類可讀、可討論的規格文件，讓開發、測試、產品基於相同理解協作。
> 這份 spec 的目的是講清楚「要做什麼、如何驗證」。

不是測試程式碼，不是實作，不是工具選型。任何一段內容如果不服務上面那句話，就不該出現在 spec 裡。

一句抽象敘述可以有十種解讀，一個具體範例只有一種。範例同時是「規格」與「未來測試的種子」：

| ❌ 抽象規格 | ✅ 具體範例 |
|---|---|
| 系統應該快速回應 | 使用者點擊送出後，頁面在 2 秒內完成導向 |
| 使用者可以提款 | 帳戶餘額 1000、提款 500 → 成功，餘額變 500 |
| 登入功能應該安全 | 連續輸入錯誤密碼 5 次後，帳戶鎖定 15 分鐘 |

## 1. 命名與編號（先讀這段，其餘全部建立在它上面）

三層 ID，**點號左邊是規則、右邊是案例**：

| ID 樣式 | 意義 | 讀法範例 |
|---|---|---|
| `US-<角色>-<n>` | User Story，依角色分組 | `US-Operator-2` = Operator 這個角色的第 2 條 story |
| `FR-<n>` | Functional Requirement，功能性業務規則，全文件流水號 | `FR-3` = 第 3 條功能規則 |
| `NFR-<n>` | Non-Functional Requirement，獨立流水號 | `NFR-1` = 第 1 條非功能規則 |
| `FR-<n>.N<i>` | Normal，該規則的正常案例 | `FR-3.N1` = FR-3 的第 1 筆正常案例 |
| `FR-<n>.E<i>` | Edge，該規則的邊界案例 | `FR-3.E2` = FR-3 的第 2 筆邊界案例 |
| `FR-<n>.F<i>` | Fail，該規則的失敗案例 | `FR-3.F1` = FR-3 的第 1 筆失敗案例 |

`<角色>` 用一眼看得懂的完整單字（`Operator`、`Viewer`、`Admin`），不為了短而縮寫。

**三條硬規則：**

1. 案例 ID 一律掛在規則底下，序號在該規則內從 1 起算。看到 `FR-7.F2`，搜尋 `FR-7` 就直接到現場，不必全文找。這是整套編號存在的主要理由。
2. ID 只增不改。規則作廢就在標題標 `FR-5 (deprecated)` 並保留條目，號碼不回收、不重編。ticket、PR、測試名稱裡的引用才不會爛掉。
3. 關聯寫在內文，不寫進 ID。一條規則服務哪些 story，用規則區塊的 `Story` 欄位表達。story 增減時 ID 不動。

為什麼不把 story 綁進規則 ID（例如 `FR-Operator2-1`）：一條規則後來多服務一個 story 就得改 ID，所有引用跟著爛；而且「這條規則比較貼近哪個 story」是主觀判斷，兩個人編出來的號碼會不一樣。改用「扁平 ID + 每條規則的 `Story` 欄位」，關聯性寫在看得到的地方，比藏在 ID 裡好查也好改。

為什麼案例序號不做全文件連號：在 FR-2 中間插一筆正常案例，後面所有規則的序號都要重編；而且看到 `N7` 不知道它屬於誰。代價是無法用單一序號看出「全文件第幾筆案例」——這個資訊本來就沒人需要。

## 2. 規格文件骨架

依此順序產出，命名固定，區塊可依情境增減：

| # | 區塊 | 一句話目的 |
|---|---|---|
| 1 | 功能背景 | 功能／作為／我想要／以便於 |
| 2 | Problem Statement | 使用者視角的問題 |
| 3 | Solution | 使用者視角的解法 |
| 4 | User Stories | 窮舉需求，依角色編號，供後面的規則引用 |
| 5 | **業務規則與情境** | 核心：規則 → GWT → Examples，三者同區塊 |
| 6 | Implementation Decisions | 模組／介面／schema／API 合約（不含檔案路徑與程式碼） |
| 7 | Testing Decisions | 測什麼、在哪個 seam 測、prior art（不含測試碼） |
| 8 | Out of Scope | 明確排除項 |
| 9 | Open Questions | 待確認問題表 |
| 10 | Further Notes | 其他補充 |

粗體那塊是這份 spec 的重心，其餘都是為了讓它讀得懂。

### 一次產出，之後再討論

一次把整份寫完再交出去，不要邊寫邊停下來問。不確定的東西有兩個去處：判斷題寫進 Open Questions，選擇題寫成選項表（見 Testing Decisions 的接縫）。停下來問會讓對方拿到半份文件，而半份文件討論不起來。

唯一該先問的情況：連「這功能要解決什麼問題」都不知道。那不是不確定，是還沒開始。

寫完之後整份都可以改——spec 是拿來討論的，不是拿來拍板的。結尾主動邀請修正。

### 精簡版：需求只有一條規則時

不是每個需求都值得一份 10 區塊的文件。先把規則列出來，只有一條、而且只服務一個角色，就用精簡版：

| | 完整版 | 精簡版 |
|---|---|---|
| 出哪些區塊 | 全部 10 個 | Rule / Given-When-Then / Examples，加結尾的「還要不要補」 |
| 什麼時候用 | 兩條以上規則，或牽涉多個角色、多個系統 | 一條規則、一個角色 |

精簡版不要為了湊格式生出 Problem Statement 和只有一條的 User Stories。那些區塊存在的理由是「多方要對齊」，一條規則的需求沒有那個問題，硬補只會讓人略過整份文件。

升級時機：寫 Examples 的時候發現撐出了第二條規則，或對方追問的情況屬於另一個角色，就改用完整版重寫，並說一句為什麼升級。

## 3. 各區塊怎麼寫

### User Stories（骨架 #4）

要「長」。窮舉不同角色、不同權限、不同狀態下的需求，不是三五條交差。每條格式固定：

```markdown
- **US-Operator-1**：作為 <角色>，我想要 <功能>，以便於 <好處>
```

依角色分組，同組內連號。先把 ID 編出來，下面的規則才有東西可指。

✅ 完成判準：每個在 Problem Statement 出現過的角色，都至少有一條 story。

### 業務規則與情境（骨架 #5）★ 核心

每條規則都用同一個版型，讓讀者掃過去就知道每段在哪：

````markdown
### FR-1｜提款金額不得超過可用餘額

**Story**：

- US-Holder-1（提款拿到現金）
- US-Holder-3（不會被扣到超額）

**Rule**：提款金額 ≤ 可用餘額時放行並扣款；超過則整筆拒絕，餘額不變。

**Given-When-Then**

```gherkin
Given 帳戶可用餘額為 <balance>
When  持卡人提款 <amount>
Then  交易結果為 <result>
And   帳戶餘額變為 <balance_after>
```

**Examples**

| ID | balance | amount | result | balance_after |
|---|---|---|---|---|
| FR-1.N1 | 1000 | 500 | 成功 | 500 |
| FR-1.E1 | 1000 | 1000 | 成功 | 0 |
| FR-1.E2 | 1000 | 0 | 拒絕：金額須大於 0 | 1000 |
| FR-1.F1 | 1000 | 1500 | 拒絕：餘額不足 | 1000 |
````

版型規則：

- 標題是 `FR-<n>｜一句話`，一句話要能單獨看懂這條在管什麼。
- 四個標籤固定：`Story` / `Rule` / `Given-When-Then` / `Examples`。四個都是 Gherkin／SbE 的既有詞彙。
- **每個標籤自成一段，段與段之間空一行。** 只換行不空行時，多數 Markdown 渲染器會依 soft line break 把兩段併成一行，變成「Story：⋯⋯ Rule：⋯⋯」黏在一起。
- `Story` 固定用 bullet list，一行一個，只有一個 story 時也一樣：

    ```markdown
    **Story**：

    - US-Operator-1（擋機器流量）
    - US-Operator-2（拒絕要可歸因）
    - US-Viewer-1~4（真實觀眾不被誤擋）
    ```

  不留單行版是因為：規則長大時 story 只會愈列愈多，遲早得改成清單，兩種格式並存只會讓同一份文件前後長得不一樣；而且一行一個才有位置放各自的理由。
- 同 kind 連號三個以上，可用 `~` 縮寫成一個項目：`US-Viewer-1~4`。只能用在連號且同 kind，指 1、2、3、4 全部，不是「1 到 4 之間某幾個」。
- Rule 只寫「系統做什麼」，業務理由寫進 Story 的括號裡。分不出來時用這個判準：**把那句話刪掉，Examples 需不需要跟著改？**
  - 不用改 → 那是理由。「不為機器流量付費」刪掉，案例一列都不動，它解釋的是這條規則為什麼存在。寫成 `US-Operator-2（擋機房與爬蟲，不為機器流量付費）`。
  - 要改 → 那是規則。「`datacenter`、`cdn_edge`、`crawler` 拒絕」改成連 `consumer_vpn` 也擋，Examples 立刻要多一列 F 案例。
- 怎麼避免混在一起——三個機械檢查，不靠自覺：
  1. **Rule 預設一句話；要寫第二句，先確認它對得到案例。** 對得到 → 它是同一個機制的補充條件（TTL、逾時、預設值），留著。對不到 → 它是理由（移走）或第二條規則（拆開）。句數本身不是問題，「沒有案例撐著的句子」才是。
  2. **看到「因為、由於、避免、以免、為了、這樣才能」就停。** 這些連接詞後面幾乎都是理由，它們是最常見的入侵路徑。
  3. **交稿前每條 Rule 跑一次刪除測試。** 這是最後一道，前兩道漏掉的會在這裡被抓到。
- 理由不是不能寫，是要放對地方。依份量決定去處：

  | 理由的份量 | 去處 |
  |---|---|
  | 一個詞組 | Story 項目的括號 |
  | 一兩句、只跟某幾筆案例有關 | Examples 表格後面的說明段，指名案例 ID |
  | 整個功能為什麼要做 | Problem Statement |
  | 選了 A 沒選 B 的取捨 | Implementation／Testing Decisions |
  | 還沒定案 | Open Questions |

  最常塞錯的是第二列：長度中等、專屬於某條規則的設計說明，塞不進括號就被順手接在 Rule 後面。正確位置是 Examples「之後」，讀者先看完案例再看為什麼。混在 Rule 裡的代價是審規格的人分不出哪句要變成測試、哪句只是背景。
- Rule、GWT、Examples 三者同一區塊，不要拆到文件不同段落。
- Examples 的欄名 = GWT 裡的 placeholder 名，一字不差。讀者才能左右對照著讀，不必翻譯。
- Placeholder 名預設用 en-US snake_case（`<balance>`、`<balance_after>`），因為它會直接變成程式變數與 test fixture 的 key，中文名到那一步還要再翻一次、容易翻歪。值照業務講法寫，中文沒問題。
- Examples 表格一律寫完整 ID（`FR-1.N1`），不要只寫 `N1`。有人在 ticket 或 PR 裡貼一行過來時，那行要能自我解釋。表格因此變寬是可接受的代價；真的寬到不能讀，代表 placeholder 太多、該拆規則了。
- **N / E / F 三類都要有**。缺任何一類，代表審視還沒做完，不是「這條規則剛好沒有」。
  - `N` = Normal，正常：主要成功路徑。
  - `E` = Edge，邊界：剛好等於上限、值為 0、剛好超過 1、空集合、重複送出、時間交界。
  - `F` = Fail，失敗：權限不足、狀態不允許、依賴故障、輸入非法。
- 非功能性規則同樣要有具體案例，`NFR-1.E1` 這種。「應該快速」不是規則，「p99 < 300ms、超時回 504」才是。

#### FR 還是 NFR

常見的分法是「NFR 是技術面、FR 是商業面」。這個直覺在功能面向使用者時剛好會對，但功能本身就是技術性的（重跑冪等、流量判定、快取失效）時整個垮掉——那種情境下每條規則都是技術面。

改用這個判準：**看 Then 寫得出來的是一個值，還是一個測量值與門檻的比較。**

| | FR | NFR |
|---|---|---|
| Then 是 | 一個值：狀態碼、欄位內容、資料列數、gate | 測量值 vs 門檻：p99 ≤ 8ms、掃描量 ≤ 單日 partition |
| 怎麼判定 | 一組輸入跑一次就知道 | 要在負載、規模或持續時間下測量分布 |
| 通常跑在 | CI | 負載測試、夜間流程 |

「技術性」「故障」「併發」「安全」都不影響歸類：

- 「儲存故障時回 503、不建立訂單」聽起來是可用性，但 Then 是狀態碼與筆數 → FR。
- 「拒絕回應不含 ISP 欄位」聽起來是資安，但 Then 是回應欄位清單 → FR。
- 「冪等檢查額外延遲 p99 ≤ 15ms」的 Then 只能用測量值表達 → NFR。

有疑慮時歸 FR。分錯成 NFR 的代價大得多——NFR 多半不進 CI，錯放進去等於悄悄失去覆蓋。

表格排不下、只有一組值、或多維組合不知道要列幾筆時，看 [references/examples-guide.md](references/examples-guide.md) 第 2 節。第一次用這個 skill、想看整份填完長什麼樣，看第 3 節的完整範例。

### Implementation Decisions（骨架 #6）

記「決策」，不記程式碼與檔案路徑——後者很快過時。要動哪些模組、介面長怎樣、schema／API 合約怎麼變、關鍵互動順序。

例外：若原型產出一段比文字更精確的片段（狀態機、reducer、schema、type 形狀），可內嵌並註明來自原型，但只留決策密度高的關鍵部分，不是可跑的 demo。

### Testing Decisions（骨架 #7）

只描述「怎麼測」，不寫測試碼或 step definitions——那是 Dev 的工作。內容包含：

- 要測的模組
- 選定的接縫（見 §5）、選它的理由、以及被否決的選項
- 程式碼庫中類似的既有測試（prior art）
- 好測試只驗外部行為、不綁實作細節

接縫是這份 spec 裡最容易選錯、也最貴的一個決定，所以不要只寫結論。列一張選項表，讓看的人能直接反駁：

```markdown
| 選項 | 接縫位置 | 能驗到的 Examples | 驗不到的 | 測試成本 |
```

表格之後給一句建議與理由，並寫明「若成本不能接受就退到哪個選項、代價是哪條規則變成手動驗證」。

「驗不到的」那一欄是重點——它把「這個選項比較快」翻譯成「這個選項會漏掉哪幾條規則」，對方才有東西可以權衡。只寫「選 A 因為它最高」是沒辦法討論的。填好的完整例子在 [references/examples-guide.md](references/examples-guide.md) 第 3 節。

## 4. 撰寫流程

§2 的骨架已經給了區塊順序，這裡只講其中真正需要判斷的四件事。四件事沒有嚴格先後——寫 Examples 時回頭改 Story、想接縫時發現規則沒寫清楚，都是正常的，不必為了照順序而重來。

**先理解脈絡。** 在既有程式碼庫作業時，先探索程式碼再動筆，別把 spec 建立在錯誤假設上；沿用專案的領域詞彙，整份用同一套用語；尊重你要動到區域的既有 ADR，不要在 spec 裡默默推翻既有決策。全新專案跳過。

**選版本。** 先把規則列出來，決定走精簡版還是完整版（見 §2）。只有在「不知道這功能要解決什麼問題」時才先問；其餘不確定一律往下寫，最後收進 Open Questions。

**戴三頂帽子攤開情境。** 只戴一頂，很容易只覆蓋 Normal。

| 視角 | 問自己 |
|---|---|
| 🎯 PO | 業務目標是什麼？核心 Normal 情境有哪些？使用者真正的意圖與價值？ |
| 🛠️ Dev | 邊界在哪？技術限制、前置狀態、併發或失敗模式怎麼體現？資料前置條件是什麼？ |
| 🔍 QA | 哪些 Edge 容易被遺漏？哪些 Fail 要覆蓋？哪些「組合」情境有風險？ |

戴 QA 帽子時，讀 [references/examples-guide.md](references/examples-guide.md) 第 1 節的檢查清單逐項掃過。憑印象想 edge case 一定會漏。

**挑接縫，並寫成可以被推翻的樣子。** 見 §5。不要停下來問，但要讓對方有東西可以反駁——接縫選錯，後面的測試決策會整串歪掉。

交出完整的一份之後，結尾問：接縫選得對嗎？範例符合預期嗎？還有哪些情境要補？

## 5. 測試接縫（Seams）

這是整份 spec 中最影響測試長期成本的一段，值得想清楚再寫。

### 定義

接縫是「你能改變程式行為、卻不必動那段程式本身」的地方。在測試語境下就是：**測試從哪個介面把輸入打進去、從哪裡觀察結果**——一個功能對外的「前門」。

### 怎麼挑（決策順序）

1. 先找既有接縫沿用，不要新開。每多一個接縫，就多一塊要維護的契約表面、多一處內部細節外洩到測試。
2. 讓「對外可觀察的行為」替你選。接縫就是 Examples 的 Given／When／Then 能被觀察到的那個介面。Examples 講的是「`POST /orders` → 201、建立訂單」，HTTP 端點就是天然接縫。
3. 取你能取的最高點。「高」= 越靠近呼叫端／使用者、越遠離實作細節。真的需要新接縫時，也在最高點提出，別為了方便往低處鑽。

| 後端／資料工程常見的高接縫 | 要避免的低接縫 |
|---|---|
| HTTP handler／端點 | 私有函式 |
| 訊息／佇列的消費入口 | repository 內部 |
| CLI 指令 | 特定 SQL 語句 |
| 對外的 package API | struct 欄位名 |
| service／use-case 的最外層邊界 | |

### 為什麼要高

- 測試能撐過重構——最大的回報。接縫定在對外行為上，測試釘住的是契約而非結構；內部隨你重寫，測試都不該壞。定太低則重構會弄壞一堆行為其實沒變的測試，製造假警報。
- 更少替身與設定——接縫越高，要 mock 的協作對象越少、前置越單純。
- 每個測試更有價值——測到的路徑接近呼叫端真正經歷的，同樣數量的測試給更多信心。
- 一個清楚的入口——新人一眼知道從哪測，不會出現重複、彼此打架的覆蓋。
- 反過來磨利 Examples——先決定接縫會逼你講清楚「對外可觀察的行為是什麼」。

### 上界與取捨

「最高」不是教條。接縫拉太高（整條 e2e、打真實 DB／網路）會變慢、變 flaky。實務上取的是「在測試仍穩定、速度仍可接受的前提下，最高的那個接縫」。若最高接縫太慢，退一階到剛好能觀察到目標行為、又不綁實作的地方。

退階時要問的不是「哪個比較快」，而是「退了之後哪幾條規則就驗不到了」。快 30 秒但漏掉整份 spec 要修的那條規則，是很差的交換。把三個選項與各自漏掉的規則列成表寫進 Testing Decisions。

理想上整個 codebase 的接縫數量越少越好——每個接縫都是一份你必須維持穩定的契約。

## 6. 禁區

- 不寫測試程式碼或 step definitions——這份 spec 是給人讀、給人討論的，實作測試是 Dev 的工作。
- 不討論自動化工具（Cucumber、SpecFlow、Behave 等）——聚焦情境本身，不是工具選型。
- 不放檔案路徑在 Implementation Decisions。
- 範例要能獨立閱讀——不需要口頭補充就看得懂條件、操作、結果。
- 語言與使用者一致（中文／英文），整份 spec 用同一套領域詞彙。
- 這是「動工前」的產物：目標是達成共識，不是產出實作。
