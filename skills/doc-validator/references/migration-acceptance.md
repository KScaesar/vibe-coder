# Migration 驗收細則

適用於有來源文件、把內容重組或拆分為多份文件的審查。主檔 `SKILL.md` 的 Validation Process 只給步驟，本文件補判斷標準與結果記錄格式。數字與門檻都是提示，依情境裁量。

## 1. 正向對照：來源 → 新文件

審查者先讀來源，再讀新文件，最後才讀實作者回報。依來源順序逐章節、逐段落回答：「這段的內容，能在新文件的某處找到嗎？」

- 不要求文字一致。被改寫、合併、拆開、移到不同類型的檔案，只要意思相同就算找到。
- 找到：記下位置，繼續。
- 找不到：先歸類，不要立刻判不合格。

### 省略清單的分類

| 類別 | 定義 | 判定 |
|---|---|---|
| 過細 | 對「目標讀者」沒有影響，例如逐行範例、重複前文的內容、與單一工具綁定的逐項注意事項。判準要指明是對哪一種讀者：只對特定語言或工具的使用者有影響，但對其他讀者沒有，要分開處理，不能一概視為過細 | 合格 |
| 過程紀錄 | 純時間序敘述、補洞用的過程用語。其中說明「為何選這個、不選那個」的理由與代價屬於決策內容，要留，可改寫成不帶版本的說法；已改寫保留理由的，記為「過程紀錄（已改寫保留）」 | 合格 |
| 明列刪除 | 使用者或交接文件事先明確列出可刪的內容（如整節索引）。仍須列入清單並引用授權出處 | 合格 |
| 其他 | 規則、行為、定義、案例、決策與其理由、使用者必須遵守的要求 | **不合格**，要補回 |

- 前三類必須出現在省略清單並說明歸類原因；審查者不同意歸類時視為「其他」。
- 清單固定欄位：來源章節、內容摘要、類別、理由、新位置（已改寫保留者才有）。

### 「找得到」的判斷標準

| 內容 | 要找到什麼 |
|---|---|
| 規則 | 同樣的條件與結果，不能只剩模糊描述 |
| 例外與邊界 | 來源明列的例外，不能只保留通則 |
| 數值與預設值 | 逾時、預設狀態碼等必須在 |
| 測試案例 | 每個案例的前置、觸發、預期的實質內容都在 |
| 圖 | 圖表達的資訊要在，不一定是同一張圖 |
| 決策記錄 | 背景、決策、後果、被拒絕的替代方案與原因都在 |

## 2. 反向對照：新文件 → 來源

完成正向對照後，從新文件反向檢查。每個檔案的實質內容都要能指到來源，並依下表分級：

| 分級 | 處理 |
|---|---|
| 有來源 | 通過 |
| 由來源直接推導 | 通過，逐句核查時標明 |
| 組合推導（把多個事實串成新結論） | 必須改寫為來源的原句意思，或登記授權 |
| 僅程式碼可佐證 | 不得進規範性文件；若要保留，改放說明性文件並註明依據 |
| 新寫的範例程式碼 | 需登記授權，可編譯並與文件逐字同步 |
| 無來源 | 不合格，移除，除非屬下列「通常接受」 |

通常接受與通常拒絕的例子：

| 通常接受 | 通常拒絕 |
|---|---|
| 銜接句、導覽、索引 | 把兩個獨立事實串成「設計目的」或「因果」的句子 |
| 為了讓類型成立的最少量改寫（如規則改寫成「目標加步驟」） | 補上來源沒有的接線程式碼或設定 |
| 只引用既有事實的整合型文章（實作者回報中說明） | 索引中整理出來源沒有的規則表 |
| 檔頭標示類型與適用範圍 | 以「看起來合理」為由新增規則 |

**逐句來源核查**針對新寫的整合文與導覽：每句標為「有來源 / 可由來源直接推導 / 無來源」，符合上表「通常拒絕」的句子必須改寫、補來源或移除。

另外檢查：
- **類型遵循度**：逐檔對照 Document Types 的 Must / Must Not，確認決策性理由在 decisions，沒有留在 reference 中重複。
- **類型名實相符**：檔案自述的性質與所在類型不一致時（例如自稱「不是逐步練習」卻放在 tutorials），改名、移動或在檔頭明確標示。
- **橫切主題**：同一主題散在多個檔案時，檢查是否有索引或匯總入口；索引的界線見 `SKILL.md` 的「導航不承載內容」。

## 3. 逐區塊比較：是否變得更好懂

只確認「沒有漏、類型正確」不夠，重構的目的是更容易理解。對來源的每個主要區塊，讀來源再讀對應的新檔案，與第 1 節的對照結果合併成一張表：

| 來源章節 | 保真結果 | 可讀性判定 | 對應位置或說明 |
|---|---|---|---|
| 章節 A | 通過 | 更好 | 新文件位置 |
| 章節 B 引言 | 通過（過程紀錄） | 相當 | 省略清單第 3 項 |
| 章節 C 末段 | **不合格** | 更差 | 找不到某個例外情境的說明 |

可讀性判定：

| 判定 | 意思 |
|---|---|
| 更好 | 重構後更容易找到、更容易理解 |
| 相當 | 差別不大 |
| 更差 | 更難懂、更難找，或需要來回跳轉才能拼出完整意思 |

判斷面向（整體裁量，不逐項打勾）：可找到性（從首頁或檔名一步到位）、理解順序（前置知識在使用處之前或有連結）、認知負擔與粒度（見 `SKILL.md` 粒度雙向裁量）、用詞編排一致，以及原文的好懂之處（一頁式總覽、圖、情境範例）是否被拆散而失去效果。

「更差」必須說明具體原因並建議修法（精確到檔案與位置）。**有未解決的「更差」不能驗收。**

## 4. Migration 專屬的機械檢查

通用項目見 [mechanical-checks.md](mechanical-checks.md)，這裡只列 Migration 才有的：

- 定義集合比對：來源與新文件中的 ID、編號、術語集合一致，差異只能是已列入省略清單的項目；新文件內每個 ID 只定義一次；總數重構前後相同（同樣扣除省略清單項目）。
- 搬運型內容（如大量測試案例）用腳本逐一比對，差異應只剩連結改寫等預期項目。
- 若約定保留來源檔案，確認它未被改動（如比對雜湊）；新文件是否可連向來源，依雙方約定。
- 索引層重疊：首頁路徑表、文件地圖、各目錄 README 是否重複列同樣的導覽，有就合併。

## 5. ADR 遷移情境

從舊文件拆出 ADR 時（ADR 的一般規則見 `SKILL.md` decisions）：

- 原文若混有時間序的版本敘事，可改寫成不帶版本的子決策，保留「為何選這個、不選那個」的理由。
- 原文沒有明確狀態的 ADR，狀態欄只寫讀者看得懂的短語，如「Accepted（推定，未見明確記載）」；找不到任何依據就寫「狀態未標註」，不可直接寫 Accepted。ADR 本文不出現「遷移」「來源文件」等遷移過程的字眼，讀者不需要知道曾有另一份文件。
- 推定的依據（例如「被現行設計說明引用為採用中」）集中寫在 decisions 索引的「狀態的依據」區塊；遷移層面的記錄（哪些狀態是推定、誰推定的）只登記在實作者回報與審查報告。

## 6. testcases 與程式連動

若測試程式或 CI 會解析文件格式（標題、ID、表格），改動檔案結構或標題時要同步修改解析端並重跑測試；新增、合併、改名檔案前，也要確認解析端的比對規則不會把索引或總表誤當成案例定義。
