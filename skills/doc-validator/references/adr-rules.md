# ADR 審查

ADR 與 reference 的差別在時間點與性質：

| 類型 | 記錄什麼 | 時間點 |
|---|---|---|
| decision（ADR） | 選擇當下的取捨 | 決策當下 |
| reference | 系統現存的事實與規則 | 決策之後 |

## 一、必須存在的四項內容

1. 當初有哪些可選方案
2. 每個方案的優缺點，包含最終被選中的
3. 最後選了什麼
4. 為什麼選這個（取捨理由）

- 標題與章節結構不限（Options、Trade-offs、Why 或不分節皆可）。
- 標題命名不得作為扣分依據，只看讀者找不找得到這四項內容。

缺陷判定：
- 缺 1、2（只有結論，沒有方案比較）：內容缺陷。
- 缺 4（沒說為何選它）：內容缺陷。
- 被選中者只有優點、沒有代價：缺 2。
- 優缺點已涵蓋後果時，不必另設後果區塊。

## 二、依賴方向

ADR 是源頭，reference、testcases 是決策之後才長出來的。
ADR 若把現存事實當依據或 Related，就是讓決策依賴自己的產物。

| 方向 | 規則 |
|---|---|
| ADR → reference／testcases | 不允許（依據、Related、內文連結皆是） |
| reference／testcases → ADR | 由它們標註「源自 ADR-xxx」 |
| explanation → ADR | 允許，單向 |
| ADR → ADR | 允許，如 supersede 或直接因果 |
| ADR → explanation | 僅限延伸閱讀，不得是理解決策的必要條件 |

- ADR 不可變，explanation 隨現況改寫；內文依賴它會讓 ADR 隨時間失真。
- ADR 要提到某條規則時，寫成選擇當下的背景事實，不放連結。
- 為自足而保留的名詞說明與背景描述，是可接受的重複（C 類）。

## 三、不屬於決策的內容

ADR 不混入以下內容，這些屬 reference 或 explanation，建議搬移（B 類）：
- 現存事實的描述
- 規則本體
- 機制流程（步驟編號、狀態轉移、參數與預設值）

判斷：這段是在說「當時為何選這個」，還是「現在系統怎樣」。後者移走。

## 四、方案來源需可確認

方案與優缺點的來源要可確認：git history、PR、對話紀錄，或使用者確認。
事後補寫或反推的 ADR 尤其要注意。

- 無法佐證的方案，向使用者確認，不可臆造。
- 使用者無法確認時，如實標明（如「事後反推」「未記錄」），列為 A 類（需決策）。
- 審查者與實作者都不代為補寫。
- 因來源無法確認而缺項：A 類。來源可確認卻沒寫：B 類。

## 審查摘要

| # | 檢查 | 判定 |
|---|---|---|
| 1 | 四項內容齊備（不論標題） | 缺漏為內容缺陷 |
| 2 | 無指向 reference／testcases 的依賴 | B 類，嚴重違規 |
| 3 | 無現存事實、規則本體、機制流程 | B 類，搬移 |
| 4 | 方案來源可確認 | 無法確認為 A 類 |
