# ADR 審查

適用條件：審查對象含 decisions（ADR）時才讀。

ADR 記錄判決，是源頭；判決之後才長出 reference 的規範與 explanation 的現況解釋。兩者的差別在時間點與性質：

| 類型 | 記錄什麼 | 時間點 |
|---|---|---|
| decision（ADR） | 判決當下的取捨 | 決策當下 |
| reference | 系統現存的事實與規則 | 決策之後 |

## 1. 必要內容：讀者要能回答的 5 個問題

1. 這個決策現在還有效嗎？（狀態，例如有效、已被 ADR-0012 取代）
2. 當時遇到什麼問題、有什麼限制？（背景）
3. 考慮過哪些做法？
4. 各做法的好處和代價是什麼，包含最後選中的那個？（後果算在代價裡，不必另寫）
5. 最後選了哪個？為什麼？

- 標題、章節、段落結構不限，甚至一段連續文字也可以；標題命名不得作為扣分依據，只看讀者找不找得到答案。
- 被選中者只有好處、沒有代價：第 4 題缺漏。
- 缺漏的歸類見第 5 節。

## 2. 不可變與修訂

- 決策內容只能追加，既有內容不改。
- 先判斷新決策回答的是不是同一個問題：新 ADR 的候選方案是否和舊 ADR 的方案爭同一個位置（例如都在回答「設定儲存用什麼」）。
  - **同一個問題，限制條件相同，對方案有新資訊**（實測數據、新版本、成本變化）而改變選擇：沿用原 ADR，原文不動，在後面追加修訂區塊。修訂區塊標示決定時間（如 `2026-10-12 13:01 +08:00`），並回答第 3~5 題；背景沿用原文，不必重寫。不標 Outdated，不另開新 ADR；下游的「源自」標註不改指向，內容以最新修訂區塊為準。
  - **同一個問題，限制條件改變**（出現新限制，或原限制消失）：
    - 選擇因此改變：開新 ADR 取代，背景寫明哪些限制改變；舊 ADR 標 Outdated 並註明取代者（如 `Outdated: replaced by ADR-0012`）。
    - 選擇不變：在原 ADR 追加重新評估區塊（標示決定時間），記錄新限制與仍選原方案的理由；不標 Outdated。
  - **不同的問題**：開獨立 ADR，不算取代，舊 ADR 狀態不變。若新決策使舊決策不再適用（例如整個元件被移除），舊 ADR 標 Outdated 並註明因哪份 ADR 失效（如 `Outdated: obsoleted by ADR-0015`）。
- **編輯性修正例外**：刪除違規連結（第 3 節）、移出不屬於判決的內容（第 4 節）不屬於改動決策內容，可直接修改，並附一行修訂註記（日期與原因）。

## 3. 連結方向

| 方向 | 規則 |
|---|---|
| ADR → ADR | 允許，如取代、修訂或直接因果 |
| ADR → 其他任何文件 | 不允許（依據、Related、延伸閱讀、內文連結皆是）；ADR 是源頭，不依賴下游，下游隨現況改寫會讓 ADR 失真 |
| reference → ADR | 出自判決的規則**必須**標註「源自 ADR-xxx」 |
| testcases → ADR | 可選；沒標不算違規 |
| explanation → ADR | 允許；用一兩句帶出結論並連結 ADR，不複製方案比較 |

- 「源自」只能指向有效的 ADR（有效或已修訂者）。已標 Outdated（被取代或失效）、否決（Rejected）或仍在提案（Proposed）的 ADR，其內容不得作為 reference 的現行規則。
- 只有確實出自判決的規則才標「源自」。規則沒有對應的 ADR 不算缺陷，不要求補寫 ADR。
- ADR 要提到某條規則時，寫成選擇當下的背景事實，不放連結。
- 為自足而保留的名詞說明與背景描述，是可接受的重複（C 類）。

## 4. 不屬於判決的內容

ADR 不混入現存事實的描述、規則本體、機制流程（步驟編號、狀態轉移、參數與預設值）。判斷：這段是在說「當時為何選這個」，還是「現在系統怎樣」；後者移出 ADR（編輯性修正，見第 2 節），依 `SKILL.md` Document Types 的定義歸到所屬類型。本文件不指定去處。

## 5. 方案來源需可確認

方案與優缺點的來源要可確認：git history、PR、對話紀錄，或使用者確認。事後補寫或反推的 ADR 尤其要注意。

- 無法佐證的方案，向使用者確認，不可臆造；審查者與實作者都不代為補寫。
- 使用者無法確認時，如實標明（如「事後反推」「未記錄」）。
- 缺漏因來源無法確認：A 類。來源可確認卻沒寫：B 類。

## 6. 從舊文件拆出 ADR（僅 Migration）

- 原文混有時間序的版本敘事時，依第 2 節的三種情況拆寫：限制相同、因方案新資訊改變選擇的，寫成修訂區塊；限制改變而改變選擇的，寫成取代關係的新 ADR；不同問題的，拆成獨立 ADR。保留「為何選這個、不選那個」的理由。
- 原文沒有明確狀態的 ADR，狀態欄只寫讀者看得懂的短語，如「Accepted（推定，未見明確記載）」；找不到任何依據就寫「狀態未標註」，不可直接寫 Accepted。ADR 本文不出現「遷移」「來源文件」等遷移過程的字眼，讀者不需要知道曾有另一份文件。
- 推定的依據（例如「被現行設計說明引用為採用中」）集中寫在 decisions 索引的「狀態的依據」區塊；遷移層面的記錄（哪些狀態是推定、誰推定的）只登記在實作者回報與審查報告。
