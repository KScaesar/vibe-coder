# doc-validator

驗證文件是否把「對的內容放在對的地方，並保持適度粒度」，且讀者實際用得起來。核心做法：每份文件先歸類並評估粒度，再做機械檢查與讀者情境走查，最後輸出違規清單與搬移 / 拆分 / 合併建議。

只看「歸類是否正確」不夠：歸類對、內容卻在搬移中遺失，或讀者仍找不到東西，都會讓文件無法交付。所以本技能同時檢查內容歸屬、來源保真、讀者可用性三件事。

每條規則只在一處定義，其他章節與 references 僅引用。references 只放條件成立時才需要讀的內容，各檔開頭寫明適用條件。

## Core Principles

- **單一職責**：一份文件只服務一種讀者需求。混雜會讓讀者在需要時找不到、在不需要時被干擾。
- **單一事實來源（Single Source of Truth，SSOT）**：每個事實只在一份文件中完整定義，該文件即為它的權威來源；其他文件需要時只引用並連結回來源，不另存副本。副本一旦與來源各自演進，就會產生互相矛盾的說法，讀者無從判斷哪個才對。允許少量連結式交叉說明（一兩句點出關聯並連回來源），不算違反 SSOT。
- **粒度雙向裁量**：拆分混雜內容的同時，也要避免兩個極端，以閱讀順暢、心智負擔最低為準。
  - 過度碎片化：同類型且緊密關聯的小主題應優先合併。訊號：同一概念散在 ≥3 檔、完成一個任務需開 ≥4 個必要檔、單檔 <20 行且只有指標。「必要檔」計法見「讀者走查」。
  - 過度合併：合併後單檔過長且多主題（約 >200 行）、或合併造成自我連結，同樣要拆。
  - 最終以「依序讀完一個主題要開幾個必要檔、來回跳轉幾次」判斷。
- **導航不承載內容**：intent-doc 只做分流與跳轉。橫切索引只列項目與一句話並連到來源；索引中若整理出新的規則表，就算整合型文章，需有授權或逐句可溯源。
  - **橫切主題要有入口**：同一主題散在多個檔案時，要有索引或匯總入口。哪些主題算橫切由審查者判斷，不是機械檢查項目。

## Document Types

### Part 1: Diataxis 框架

來源：
- Diataxis 官方 https://diataxis.fr/ （tutorials-how-to、reference-explanation 兩篇差異專題特別有助於判斷模糊案例）。
- Divio Documentation System https://docs.divio.com/documentation-system/introduction/ （四象限的原始介紹，提供「各類型只有一個任務」的原則）。

僅包含 tutorials、guides、reference、explanation 四個象限。

核心原則：每一類文件只有一個任務，各自需要不同的寫法，必須明確分開、互不混雜。讀者在使用過程的不同階段需要不同類型的文件，混雜會讓文件被同時往多個方向拉扯。

分類原則：依「學習 vs 工作」與「行動 vs 認知」分類，而非按難度。tutorials 與 guides 的分界是「學習體驗 vs 生產任務」，不是入門 vs 進階。

下列 Must Not 皆指「內嵌大段內容」；一兩句連結式交叉說明可接受。各類型的「關鍵要素」是檢查內容有沒有涵蓋的參考，不是必須照抄的章節模板；只要大方向歸類正確、要素有被涵蓋，寫法不受限。

#### tutorials
- **Purpose**：帶新手取得第一次成功（學習 + 行動）。
- **Reader**：零心智模型，不預設工具背景與排錯能力。
- **Environment**：完全受控，固定版本與素材，無外部變數。
- **Must**：單一線性路徑；每步有預期輸出；承諾必定成功；卡住即視為文件缺陷（責任在作者）；結尾導向 guides 與 explanation；語氣溫和、陪伴式。
- **Must Not**：解釋架構原理、提供分支或替代方案、省略基礎指令、依賴未固定版本的外部資源。
- **關鍵要素**：前置準備、最小可用步驟、預期輸出驗證、下一步導流。

#### guides
- **Purpose**：完成特定生產任務（工作 + 行動）。
- **Reader**：有基礎能力，已知目標。
- **Environment**：真實世界，含依賴衝突與不可控變數。
- **Must**：包含真實條件分支（如 Docker vs 裸機）；假設讀者有能力，不重複解釋基本指令；參數連結至 reference；需要原理說明處連結至 explanation（僅連結，不內嵌論述）；語氣專業、俐落。
- **Must Not**：列全量參數字典、論述架構演進。
- **關鍵要素**：前置條件、操作步驟（含分支）、成果驗證、疑難排解。

#### reference
- **Purpose**：提供權威、客觀的事實規格（工作 + 認知）。
- **Reader**：知道自己在查什麼。
- **Environment**：無環境依賴，結構鏡像程式碼。
- **Must**：精確、即時更新；以清單、簽名、結構化欄位呈現；條目附相關 guides 與 explanation 連結（僅連結，不內嵌論述）；出自判決（ADR，見 Part 2）的規則標註來源 ADR，規則見 [references/adr-rules.md](references/adr-rules.md) 第 3 節。
- **Must Not**：操作教學、主觀評價或建議、設計理由、歷史、替代方案權衡、類比與命名由來。
- **注意別過度執行 Must Not**：「行為前提」是事實，應留在 reference，例如「某操作不會等待進行中的另一操作完成，呼叫端必須自行處理競態」。要移走的是「為何這樣設計」的理由與取捨，不是使用者正確使用所必須知道的行為約束。審查者若要以「reference 含理由」判違規，必須在報告寫出判斷依據；判斷不出來就歸 C 類保留，不判違規。
- **判斷兩問（兩問都要答）**：
  1. 拿掉這句，讀者是否可能誤用？會，候選留下。此問只能篩出該留的句子。
  2. 這句是在說「系統現在怎樣、使用者必須怎麼做」，還是「為何如此 / 設計上應當如此」？後者（設計理由、建議、評價）移走並改連結；前者（含呼叫端必須遵守的義務）是契約，留下，不論文件有沒有宣告 metadata。此問篩出該移的句子。
- **概念模型的歸屬**：reference 與 explanation 同屬認知（理論）那一半，「這是概念」不能用來區分兩者；區分看文字的功能。
  - 名詞定義、狀態模型、執行順序與成立條件，只要是契約的一部分（違反會誤用或出 bug），屬 reference。
  - 類比、命名由來、動機、「常見誤解」式的糾錯敘事、為何不選其他設計，屬 explanation。
  - 同一事實可以兩邊各有一句：事實句（如「兩者沒有連動」）留 reference，教學或說服的語氣移走。
- **使用者情境**：讀者是在工作中查證（reference），還是靜下來學習、建立理解（explanation）。reference 是被查閱的，不是從頭讀到尾的；整份依序敘事、帶「讓讀者想通」語氣者，視為 explanation 漂移。
- **混合文件**：reference 內連續一段以建立直覺為目的的敘事，標為 explanation 漂移，建議抽成獨立 explanation 頁並在原處連結；不得因「讀者需要先理解」而留下。僅少數句子漂移時抽句即可，不必拆檔。
- **關鍵要素**：簽名宣告、參數規格（型別 / 預設值 / 約束）、回傳結構、錯誤碼、最小調用範例。

#### explanation
- **Purpose**：說明系統為何如此設計與取捨（學習 + 認知）。
- **Reader**：有實作經驗，想理解全局。
- **Environment**：抽象的思考空間。
- **Must**：主題式論述；多角度與替代方案權衡；提及具體實踐或操作場景時連結至 guides；提到模組時連結其 reference；提到歷史選型時連結 decisions 對應的 ADR，寫法見 [references/adr-rules.md](references/adr-rules.md) 第 3 節。
- **Must Not**：逐步操作指令、速查參數表、只談單一元件細節。
- **關鍵要素**：背景與挑戰、核心機制、為何這樣設計（取捨）、替代方案對比。

### Part 2: Engineering Governance

來源：工程治理實務，不屬於 Diataxis，獨立於四象限之外，用來隔離會污染四象限的內容。包含 decisions、testcases 兩個目錄。

分類原則：現況與歷史分離。explanation 描述系統「現在」如何運作；歷史決策進 decisions/。測試細節進 testcases/，不進 guides。

#### decisions
- **Purpose**：決策紀錄，以 ADR 格式撰寫。ADR 記錄判決，是源頭；reference 的規範與 explanation 的現況解釋是判決之後的下游。
- 必要內容、不可變與修訂方式、連結方向、不屬於判決的內容、遷移規則，一律見 [references/adr-rules.md](references/adr-rules.md)（審查對象含 ADR 時讀）。

#### testcases
- **Purpose**：系統行為的客觀驗收契約，服務 QA、CI 與核心開發者。
- **Must**：邊界案例、異常斷言、覆蓋矩陣皆留在此；覆蓋矩陣（需求或不變式對應到案例）與各案例自己標註的對應需求（如 Covers 欄位）雙向一致；案例有穩定 ID。標註來源 ADR 為可選，見 [references/adr-rules.md](references/adr-rules.md) 第 3 節。
- **Must Not**：教使用者操作。「如何執行測試」屬 guides；「輸入輸出型別」屬 reference。
- **關鍵要素**：前置條件、輸入邊界、預期斷言行為。
- **程式連動**：若測試程式或 CI 會解析文件格式（標題、ID、表格），改動檔案結構或標題時要同步修改解析端並重跑測試；新增、合併、改名檔案前，也要確認解析端的比對規則不會把索引或總表誤當成案例定義。

### Part 3: Intent-doc

來源：自訂設計，不屬於 Diataxis，Diataxis 本身沒有規定讀者動線。

intent-doc 是中央路由器，把讀者導向 Part 1、Part 2 的各類型文件。載體為文件首頁 `index.md` 或倉庫根目錄 `README.md`。目標：讀者只靠首頁就能判斷該走哪條路徑。

**三條閱讀路徑**：`entry` 是入口，`flow` 是建議順序（非強制）。箭頭編號是離開當前文件的原因：(1) 想確認是否適用，(2) 已有手感要處理真實情境，(3) 需確認精確規格，(4) 想知道為何這樣運作，(5) 遇到例外或極端情境。

```text
[Top-down]    先全貌、後細節（評估工具、接手新領域）；Top-down 讀者不應被迫先動手練習
  entry : explanation
  flow  : explanation --(1)--> guides --(3)--> reference --(5)--> explanation

[Bottom-up]   先體感、後原理（照範例跑出第一個成功）
  entry : tutorials
  flow  : tutorials --(2)--> guides --(3)--> reference
              |                  +--(4)--> explanation
              +--(4)--> explanation   （tutorials 結尾可直接導向）

[Task-driven] 先任務、後必要資訊（異常排查）
  entry : guides
  flow  : guides --(3)--> reference
             +--(4)--> explanation
```

各類型條目之間的補充連結不限於圖中箭頭，以各類型的 Must 為準。

**必備**（intent-doc 的靜態檢查只看這兩項）：
1. **一句話定位**：這是什麼、給誰用、解決什麼問題。第一次接觸的讀者沒有這句就無從判斷要不要往下讀。小型專案也不可省略。
2. **入口找得到**：專案實際提供的每一種類型，從首頁都找得到入口，且入口文件有連結通往上圖中的跳轉目標。專案沒有的類型不要求入口；有卻連不到，不論專案大小都是違規。

**建議**（不要求照抄）：Hero 雙軌入口（tutorials 與 explanation 並列）、任務路由表（常見任務對應 guides）、四象限全域目錄、通往 decisions/ 與 testcases/ 的治理入口。

**倉庫根目錄 `README.md`** 是精簡版：一句話定位、極簡 quickstart、架構摘要與各目錄跳轉連結，不貼全量 API 字典或完整安裝手冊。審查 README 只看：是否肥大、有無一句話定位、能否連到專案提供的各類型入口。

**首次接觸可用性**（讀者能否只靠首頁及其連結找到第一個動作）不做靜態判斷，由讀者走查的第一類任務判定，見「讀者走查」。

### 目錄與命名

目錄與檔名風格統一，預設全小寫；`README.md`、ADR 編號檔等通行慣例不算違規。四象限目錄名以 tutorials、guides、reference、explanation 為準，`how-to` 等官方同義命名只要全專案一致，不判違規。其餘目錄為 decisions、testcases。

## Validation Process

### 模式

- **Audit**：只有現成的文件，審查歸屬、粒度、內容要素與可用性。
- **Migration**：有來源文件（如單一大檔被拆成多份文件），除 Audit 的檢查外，必須加做「來源保真」與「反向可追溯」，細則見 [references/migration-acceptance.md](references/migration-acceptance.md)。
- 有實作者或多輪審查時，另遵守 [references/review-protocol.md](references/review-protocol.md)。

### 步驟

1. **Identify & Granularity**：判定每份文件的類型與粒度。無法歸類或橫跨兩類者標記為混雜並建議拆分；多份同類型文件內容過少、零散且業務邏輯緊密相依，標記過度碎片化並建議合併；合併後過長或多主題者標記過度合併。
2. **Validate boundaries**：對照 Document Types 的 Must / Must Not 檢查內容污染，搬移方向見下方「污染搬移對照」。同時檢查**類型名實相符**：檔案自述的性質與所在類型不一致時（例如自稱「不是逐步練習」卻放在 tutorials），改名、移動或在檔頭明確標示。
3. **Validate content elements**：檢查內容是否涵蓋該類型的關鍵要素。不要求固定的章節結構、標題或順序；只有缺漏會讓讀者無法完成該類型的任務時，才算缺漏。條件式檢查：
   - 審查對象含 ADR：依 [references/adr-rules.md](references/adr-rules.md)。
   - 文件 front matter 有宣告 metadata：依 [references/doc-metadata.md](references/doc-metadata.md) 檢查宣告與內容是否一致；未宣告則略過，不扣分。
4. **Mechanical checks**：見下方「機械檢查」。
5. **Source fidelity（僅 Migration）**：逐段對照來源與新文件，不要求逐字，但每段內容都要能找到去處；只在來源出現一次的規則最容易遺失，要特別對照。同時檢查新文件有沒有來源沒有的推論、目的句或規則，不因「看起來合理」放行。細則見 [references/migration-acceptance.md](references/migration-acceptance.md)。
6. **Reader walkthrough**：見下方「讀者走查」。此步通常找到最多問題，不可用靜態檢查取代。
7. **Executable content**：見下方「可執行內容驗證」。
8. **Report**：依「輸出格式」回報違規。

審查整個 docs/ 時，先檢查 intent-doc 與目錄結構，評估整體粒度，再逐份檢查文件。

### 污染搬移對照

步驟 2 發現污染時的搬移方向：

| 發現 | 搬至 |
|---|---|
| tutorials 含架構原理 | explanation |
| guides 含全量配置清單 | reference |
| guides 含大量測試斷言 | testcases |
| testcases 含「如何執行測試」教學 | guides |
| reference 含操作教學 | guides |
| reference 含心得或建議 | explanation |
| explanation 含操作步驟 | tutorials 或 guides |
| explanation 含過期歷史 | decisions |
| ADR 含現況事實、規則本體、機制流程，或連到 ADR 以外的文件 | 移出 ADR（編輯性修正），內容依 Document Types 定義歸位；見 [references/adr-rules.md](references/adr-rules.md) 第 2、4 節 |
| 同一事實完整出現在多處 | 保留在權威來源（SSOT），其餘改連結 |

### 機械檢查

能用工具的用工具，不靠肉眼目測，讓「一致」「沒有殘留」這類結論有工具輸出可查。

- **輸出差集，不只輸出通過或不通過**：例如雙向比對要列出「A 有 B 沒有」與「B 有 A 沒有」兩份清單。
- **腳本放在暫存區，不進專案**；遵守專案既有的執行環境規則。
- 無法機械化的項目由審查者判斷，並標明是判斷而非工具結果。

| 項目 | 怎麼查 | 輸出 |
|---|---|---|
| 連結與錨點 | 逐檔解析連結，確認目標檔案與標題存在。非英文標題的錨點轉換規則要先用一個已知頁面校準 | 死連結、壞錨點清單 |
| 自我連結 | 檔案連到自己 | 清單 |
| 孤兒檔 | 統計每個文件的入站連結數；入站只來自目錄頁或索引的，確認從 intent-doc 可達 | 入站為 0 或不可達的清單 |
| 殘留 | 重構後搜尋舊章節編號、舊檔名、舊路徑 | 匹配行與位置 |
| 覆蓋矩陣 | 矩陣與各案例標註的對應需求雙向重算，逐格比對 | 格數與不同格數，列出差異格 |
| 外部引用 | 程式註解、README 指向的路徑是否存在；程式端改動以差異確認只涉及預期範圍 | 缺失路徑、非預期改動 |
| 解析端相容 | 見 testcases 的「程式連動」；跑解析端測試，確認讀到的是新位置而不是被跳過 | 測試結果與讀到的檔案數 |
| 重複事實 | 無法完全機械化：用關鍵句搜尋找候選，再由審查者判斷是否違反 SSOT | 候選清單，標明為判斷 |

Migration 另加 [references/migration-acceptance.md](references/migration-acceptance.md) 第 4 節的項目。

### 讀者走查

由沒參與撰寫、也沒看過來源的讀者，只靠被審查的文件完成代表性任務，回答「讀者能不能找到、讀懂、做完」。Audit 與 Migration 都要做。

**誰來當讀者**
- 審查者讀過全部文件（Migration 還讀過來源），不可充當讀者；Audit 亦同。
- 讀者由使用者提供，或由審查者派出全新 context 的 subagent。一個讀者只用一輪，重審要換新讀者。
- 交給讀者的說明一律使用 [references/reader-brief.md](references/reader-brief.md)，不要讓讀者讀本檔：本檔含任務設計與指標，讀者看到會失去測試意義。
- 派遣 agent（讀者、實作者、其他審查者）時：完成以預期輸出檔出現為準，不採信工具回報的「done」；給確認過的絕對路徑，避免不同 agent 寫到不同位置。
- 取不到讀者：驗證缺口，判定「未能判定」，見「判定與信心指數」。

**隔離**
- 禁讀清單（由審查者掌握，不寫進讀者說明，以免透露文件有來源）：來源文件、既有的審查報告與實作者回報、原始碼與設定目錄，以及任何會透露「文件是從哪裡來」的檔案。審查者以「只開放被審查目錄」的方式交代讀者，並用下列稽核確認。
- 在乾淨的工作目錄、沒有自動注入的環境執行。工具環境可能在讀者讀第一個檔之前，就注入版本控制狀態、近期提交訊息、專案層級說明檔，讀者因此已知有來源被拆分；做不到隔離就在報告註明「讀者事前已知」，並保守評分。
- 審查者對照讀者的工具呼叫紀錄，確認讀者回報的「違規：無」屬實（subagent 用對話紀錄或派遣工具的輸出；人請對方提供開啟檔案的歷史）。違規者的結果只當旁證，不採計並記錄；取不到紀錄時註明「隔離未能稽核」，同樣保守評分。
- 讀者環境若缺少搜尋或列檔工具，替代做法寫在任務說明裡，不由讀者自行推定。

**任務設計**
- 由審查者設計 5–7 題，涵蓋專案實際提供的閱讀路徑，以「讀者症狀」描述，不使用文件自己的詞彙；否則走查只是在驗證文件的路徑表自洽。
- 至少包含五類：
  1. 第一次接觸：只靠首頁及其連結回答「這是什麼、給誰用」並找到第一個動作。
  2. 故障排查：從症狀出發找到處理方式。
  3. 陷阱題：答案不在文件內，用來偵測讀者憑模型記憶猜答案。
  4. 依序讀完一個主題。
  5. 跨角色或跨語言題：例如不使用文件主要語言的實作者。
- 走查前先寫好每題的期望答案與必要檔集合。

**計數與完成判定**（由審查者依讀者的路徑表計算，不由讀者自評）
- 「必要檔數」只計 opened（定義見讀者說明）且屬於回答所需的檔案。首頁（intent-doc）算 1 個，因為讀者從它開始；首頁以外的導覽頁與索引頁不計。
- 第一次接觸題的指標是必要檔數 ≤3。agent 沒有時間感，不用時間計。
- 「跳轉次數」是讀者從一個檔案切到另一個檔案的次數，與必要檔數一起反映來回拼湊的程度。
- 「完成」由審查者依期望答案判定；信心層級為「猜測」者不算完成。

**缺口歸類**：所有未完成的任務、所有卡點，以及信心層級為「推得」或「猜測」的答案，都依下列歸類：

| 情況 | 類別 | 處理 |
|---|---|---|
| 文件有寫，讀者找不到或讀不懂 | B（導覽／編排） | 建議修法精確到檔案與位置 |
| 文件沒寫；Migration 的來源有 | B（搬移遺失） | 補回，並回頭檢查省略清單為何沒列 |
| 文件沒寫；Audit 中程式碼或設定可確認 | B（補寫） | 依程式碼或設定補寫 |
| 文件沒寫；來源也沒有，或只有作者知道 | A | 附審查者自己取得的證據，列為「待使用者決策」 |

### 可執行內容驗證

文件內的程式碼、指令與設定範例，在不改動被驗證專案的隔離環境中實際執行：

- 使用臨時目錄或獨立模組，以本地路徑參照被驗證專案，不寫入專案目錄。
- 逐字取用文件中的區塊，不手動修補後才執行；需要的接線若文件沒有寫，本身就是缺漏。
- 範例若被固化進專案，需有測試確認文件區塊與範例檔逐字同步，並留意排版差異（縮排、空白）造成的假性失敗。
- 與讀者走查分工：走查只讀不跑，不得宣稱範例「可執行」或教學「可用」；「範例是否可執行」以這裡的執行結果為準，「讀者能否找到、讀懂、做完」以走查為準，兩者都納入可用性軸。

## Validation Checklist

逐項檢查；每項出現問題時，依「裁量」評估對讀者的實際影響來決定扣分，不是出現即不合格。硬規則與未能判定見「判定與信心指數」。

- [ ] 每份文件只屬於一個類型，無跨類型污染，且沒有把行為前提誤當設計理由移走
- [ ] 類型名實相符：檔案自述性質與所在類型一致，不符者已改名、移動或標示
- [ ] 粒度適中：無多職責過載、無過度碎片化、無過度合併
- [ ] 符合 SSOT：每個事實只有一個權威來源，其餘為連結
- [ ] 內容涵蓋各類型的關鍵要素，Cross-link 符合各類型 Must
- [ ] 機械檢查通過：無死連結、壞錨點、自我連結、舊檔名殘留；文件皆有入站連結且從導覽找得到
- [ ] 橫切主題有索引或匯總入口（判斷項）
- [ ] 讀者走查：代表任務皆能完成；未完成者依「缺口歸類」處理；沒有取得讀者列為驗證缺口
- [ ] Migration：無硬規則項目；其餘新增內容依 [references/migration-acceptance.md](references/migration-acceptance.md) 第 2 節處理
- [ ] 審查對象含 ADR 時：符合 [references/adr-rules.md](references/adr-rules.md) 的審查摘要
- [ ] 僅在文件有宣告 metadata 時適用：宣告與內容一致（見 [references/doc-metadata.md](references/doc-metadata.md)）
- [ ] 外部引用（程式註解、README、CI 解析）的路徑與格式仍有效；文件內的可執行內容已在隔離環境驗證
- [ ] intent-doc 符合「必備」兩項、README 保持精簡（見 Document Types Part 3）
- [ ] 目錄與檔名風格一致（見「目錄與命名」）

## 判定與信心指數

### 判定標準

判定標準分三種（全文統一用這個說法）：

- **硬規則**：出現即不合格，優先於信心指數與任何門檻（含使用者自訂）。
  1. Migration：省略清單有未補回的「其他」。「其他」指被省略、但屬於規則、行為、定義、案例、決策與其理由等不可省略的內容，見 [references/migration-acceptance.md](references/migration-acceptance.md) 第 1 節。
  2. Migration：有未解決的「更差」區塊。「更差」指逐區塊比較時，重構後比來源更難懂、更難找的區塊，見 [references/migration-acceptance.md](references/migration-acceptance.md) 第 3 節。
  3. Migration：新增了來源沒有、也未獲授權的規則、行為或數值，且尚未移除、補來源或登記授權。純措辭改寫不在此列。
  4. 讀者任務因 A 類缺口做不到。補足並重驗後解除；使用者明確決定不補時轉 C 類，報告註明「任務 X 讀者做不到，使用者決定不補」。
- **未能判定**：沒有做讀者走查。這是驗證缺口（流程沒做完），不屬 A／B／C 類、不扣分，整體判定為「未能判定」；要宣稱合格必須補做走查。使用者明確同意免走查時，由使用者決定如何處理並在報告註明。
- **裁量**：其餘一切（歸類、粒度、Checklist、數字訊號）依商業邏輯與讀者情境判斷，看是否影響讀者找到、讀懂、做完；數字只是提示。

### 扣分歸因

分三類。信心指數反映「讀者能否使用」，所以 A、B 類都會影響分數；差別在歸責。驗證缺口不屬任何一類。
- **A 類**：需要使用者或作者決策、審查者與實作者無權自行補的缺口。Migration 中通常是來源本身就沒有或有歧義；Audit 中如缺少只有作者才知道的專案資訊。不歸責實作者，單獨列為「待使用者決策」，寫明它對分數的影響與補足後預期可回升的幅度。讀者任務因它做不到時適用硬規則。有實作者時的補足流程見 [references/review-protocol.md](references/review-protocol.md) 第 4 節。
- **B 類**：可以修正的問題，列入修正待辦並附預期分數。
- **C 類**：框架下的合理取捨（例如刻意保留的重複 Context），不必修、不扣分。

### 信心指數

審查結尾給一個 0-100% 的「信心指數」，代表審查者有多大把握認為這份文件（或體系）可以直接交付給讀者使用。**預設 90% 以上合格**；使用者指定其他門檻（如 95%）時以使用者為準，並在報告中註明。硬規則與未能判定優先於分數。

這是質化判斷，不是把 Checklist 勾選數或扣分表換算成百分比。讀完全部內容後，以讀者視角整體評估：讀者能否在對的地方找到需要的東西、是否會被錯放的內容誤導或卡住。一項影響重大的問題（例如 tutorials 無法照做、reference 有錯誤規格、內容遺失）可以讓分數低於門檻，即使其他項目全數通過；數個無傷大雅的小瑕疵也可能仍維持合格。

**分軸評分**：Migration 模式下，「內容保真」與「讀者可用性」分開打分並各自給理由；兩軸都要各自達標，整體才算合格，不取平均。兩軸可能差很大（例如保真高、可用性低），合併成單一分數會藏住真正的問題。Audit 模式只評可用性軸。

**可用性軸錨點**

| 信心指數 | 意義 |
|---|---|
| 95-100% | 邊界、結構、連結皆乾淨，完全確信可交付 |
| 90-94% | 僅有不影響讀者使用的微小瑕疵 |
| 70-89% | 大致可用，但有明確的邊界污染或缺漏，需修正後重審 |
| 40-69% | 多處職責混雜，或導航嚴重缺失導致讀者找不到入口 |
| 0-39% | 結構性問題，幾乎需要重寫 |

**內容保真軸錨點（僅 Migration）**

| 信心指數 | 意義 |
|---|---|
| 95-100% | 逐段對照完成；搬運型內容全量腳本比對；新增皆有來源或已登記授權 |
| 90-94% | 僅有不涉及規則、行為、數值的瑕疵（如措辭、排版） |
| 70-89% | 規則、行為、數值未變，但改寫使意思模糊，或可追溯紀錄不完整 |
| <70% | 大量內容無法追溯 |

措辭或組織方式的改寫，只要規則、行為、數值不變，不算語意被改寫。錨點只描述各分數區間的意義；合格與否一律以當次門檻判定。

**驗證覆蓋率是信心上限**：信心不能高於驗證實際涵蓋的範圍。全量用工具比對的內容，才能支持 ≥95%；只靠肉眼抽讀的區塊，上限約 93%。

**評分規則**
- 附上 2-4 句理由，說明為什麼是這個分數、最拉低分數的是什麼；每個扣分都要附證據（檔案與具體現象）。
- 分數附 ± 範圍，反映驗證的不確定性（工具全量比對範圍小，抽讀範圍大）。
- B 類預期分數要寫估算依據，同類問題跨輪分值一致；最小單位 0.5 分。預期分數只用來排修正優先序，不是機械換算（「一筆違規扣 N 分」這類換算會與質化判斷互相拉扯）。
- 未達門檻時：列出「差幾分」與「升到合格所需的最少修正」，優先列 B 類中最划算的。
- 分數剛好壓在門檻時，在理由中說明偏向哪一邊的取捨與依據。
- 資訊不足時（例如只拿到部分文件）不要硬給高分；說明受限範圍，並依已見內容保守評分。
- 修正後重審時重新評分，不沿用舊分數。

## 輸出格式

審查報告固定使用以下結構。違規編號：A 類（需使用者決策）編 A1、A2…，其餘編 R1、R2…；重審沿用同一組編號，並改用 [references/review-protocol.md](references/review-protocol.md) 第 2 節的重審模板。

```markdown
# 文件審查報告
## 摘要（整體符合度與最嚴重的 3 個問題）
## 修正待辦（B 類，依預期可收回分數由高到低）
## 違規清單
| 編號 | 檔案 | 判定類型 | 違規 | 類別 A/B/C | 預期分數 | 建議動作（搬移 / 拆分 / 合併 / 刪除） | 驗收條件 |
## 機械檢查結果（死連結 / 自我連結 / 孤兒檔 / 重複事實 / ID 一致；各項標明驗證覆蓋率：全量工具 / 抽樣）
## 讀者走查結果（任務、必要檔數、跳轉次數、卡點類別、是否完成；讀者事前已知與隔離稽核結果）
## 驗證缺口（未能執行的驗證與對判定的影響；無則省略）
## 來源保真與逐區塊比較（僅 Migration：省略清單、反向可追溯、合併結果表）
## Cross-link 缺漏
## Checklist 結果（含一行 Metadata 檢查：已啟用 / 未宣告略過）
## 信心指數（0-100% ± 範圍，門檻預設 90%）
- 分數與判定（合格 / 不合格 / 未能判定）；Migration 分軸列出
- 理由（2-4 句，扣分附證據）
- 扣分歸因（A 需決策 / B 可修 / C 合理取捨）
- 未達門檻時：差幾分與升到合格所需的最少修正
```

**範例**
Input：`docs/guides/deploy.md` 內含 40 行完整 config 鍵值表與一段 2019 年改用 etcd 的原因。
Output：R1：全量配置表屬 reference，搬至 `reference/config.md` 並於 guide 連結；R2：etcd 選型歷史屬 decisions，新增 ADR 並由 explanation 連結。信心指數 78%（不合格）：兩項污染都會讓讀者在任務中途被打斷，但步驟本身正確；完成上述兩項搬移後預期可達合格。扣分歸因：兩項皆 B 類，預期各可收回約 6.5 分（僅供排序，非換算），均由實作者修。
