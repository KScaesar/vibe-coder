# 漸進式部署並行風險審核

## 為什麼一般 review 抓不到這類缺陷

一般 review 問的是「新版寫得對不對」，而這類缺陷下新版確實是對的——錯誤只存在於「新舊同時在線」這個狀態裡。要抓到它，問題必須換成：**這兩個版本碰在一起，會發生什麼事？**

第二個反直覺之處：**造成破壞的往往是被刪除的那段程式碼。** 刪掉某段邏輯後直覺認為「刪掉就沒事了」，但並行期間它仍在舊節點上執行，而且可能正在覆蓋新節點剛寫入的結果。

依序執行 Step 0~5，最後依輸出格式回報。

**對象稱呼**：下文的「提出者」指提出此次變更的人。若審核對象就是使用者本人的變更，直接向使用者提問即可。

---

## Step 0：是否需要往下走

**本次部署期間，新舊版本會同時在線嗎？**

- 否（完整停機更新、單一實例直接替換、無契約變更的靜態資源）→ 說明理由並結束。
- 是，或無法確認 → 繼續。K8s rolling update、canary、多副本、多區域分批上線預設都是「是」。

改動大小與並行風險無關，改動的**位置**才有關；不要因為 diff 很小而跳過。

---

## Step 1：找出跨版本共用的東西

逐一確認下列三類，只要有一項為「是」就進入 Step 2。

| 類型 | 要找什麼 | 典型情境 |
|---|---|---|
| **共享狀態** | 兩版讀寫同一份資料 | 整併或搬遷儲存位置；變更寫入方式；調整資料結構或命名規則；移除同步、雙寫機制 |
| **跨版本契約** | 一版產生、另一版須能理解 | 新增、更名、移除介面路徑；調整請求與回應欄位；變更訊息格式；變更對外發出的連結格式 |
| **獨占資源** | 同時只應有一個執行者 | 排程或批次作業改由新模組負責；分散式鎖的鍵值變更；序號或識別碼產生方式變更 |

有 diff 或 repo 可讀時，從這些位置找起，不必從頭讀 business logic：

- 資料存取層、repository/DAO、client 初始化
- 鍵值與命名規則定義處（key prefix、bucket / table / topic / index 名稱、partition 規則）
- 設定檔與環境變數，**特別是被刪除的那幾行**
- 訊息 schema、protobuf / avro 定義、API route 與 handler 簽章
- 排程註冊處、分散式鎖的 key、leader election 條件

**單一最強訊號：設定中刪除了某個連線位址或資料來源。** 其次是變更描述裡出現「統一、整併、合併、改用、遷移、下線、簡化」，以及淨刪除大量程式碼。

---

## Step 2：填寫並行行為對照表

這是整個流程的核心。以文字填寫**實際行為**，不使用勾選框——問題多半在填寫過程中自己浮現，勾選框則會被無腦打勾。

| 項目 | 舊版行為 | 新版行為 | 並行期間會發生什麼 |
|---|---|---|---|
| 寫入到哪裡 | | | |
| 從哪裡讀取 | | | |
| 寫入方式（累加／覆寫） | | | |
| 產生什麼給外部使用 | | | |
| 誰負責執行（排程類） | | | |

**範例**（某系統將兩套儲存整併為一套）：

| 項目 | 舊版 | 新版 | 並行期間 |
|---|---|---|---|
| 寫入到哪裡 | A 與 B（雙寫） | 只寫 B | 兩版都在寫 B |
| 從哪裡讀取 | A | B | 各自只看到一半 |
| 寫入 B 的方式 | **覆寫**（設為 A 的值） | **累加** | **舊版持續抹除新版的成果** |

最後一欄填完，問題即無可迴避。先自己試填一遍，填不出來的格子標記為待確認，不要用「應該沒問題」補空白。

---

## Step 3：檢查被刪除的程式碼

看變更的**刪除側**。針對每一段被刪除的邏輯追問：

1. 這段程式碼在舊節點上還會執行多久？
2. 那段期間，它會對新版寫入的目標做什麼？

特別注意含有這些字樣的被刪除區塊：同步、鏡像、對齊、備援、雙寫、相容、暫時保留（sync / mirror / reconcile / fallback / dual-write / compat / legacy / TODO: remove later）。這類邏輯原本是安全備援，**但在並行期間會反轉成破壞機制**——它用自己認知的「正確值」覆蓋另一版剛寫入的結果。

粗篩指令（依環境調整）：

```bash
git diff <base>..<head> --stat                                # 變更形狀：是否淨刪除大量程式碼
git diff <base>..<head> -- '*.yaml' '*.yml' '*.env' '*.tf'    # 設定變更，注意刪除行
git diff <base>..<head> | grep -E '^-' | grep -iE 'sync|mirror|dual|backup|compat|legacy|temp'
```

---

## Step 4：判斷破壞性等級

僅在 Step 2 顯示兩版寫入同一目標時適用；若共用項目只是契約或獨占資源，此步標記為不適用，風險改由 Step 5 的階段拆分處理。

| 寫入方式 | 並行後果 | 可逆性 | 判定 |
|---|---|---|---|
| 各寫各的、彼此讀不到 | 資料分裂，兩邊各有一部分 | **可事後合併** | 高風險 |
| 相對變更（增加某個量） | 結果仍可疊加 | 可回推 | 中風險 |
| **絕對賦值（設定為某個值）** | 被覆蓋的資料直接消失 | **不可逆** | **最高：不可直接部署** |

**只要有任一版本以絕對賦值寫入共用目標，資料損毀就不是風險，而是確定會發生。** 這時措辭要明確寫「不可直接部署」，而非「建議注意」。

---

## Step 5：決定部署方式

```
Step 1 有任一項為「是」？
├─ 否 → 可直接漸進式部署
└─ 是 → 拆成三階段，每階段獨立部署且完整完成後才進行下一階段
          ① 加入對新方式的支援，但仍使用舊方式
          ② 切換為使用新方式
          ③ 移除對舊方式的支援
```

階段拆分之所以有效，是因為階段①讓兩版對同一目標的處理方式先一致下來；此後每次部署的並行狀態才是安全的。**被禁止的是「未經階段①鋪墊就直接上線」，不是滾動部署本身。**

**最常見的錯誤是把 ② 與 ③ 合併成一次部署。** 一旦合併，並行期間必然有節點無法處理新版的產出，或仍在執行即將被刪除的破壞性邏輯。

若變更引入新的產生端與消費端（新 endpoint、新 topic、新訊息型別），順序固定為**先部署消費端，再部署產生端**，否則產出物會落到還不認得它的節點上。

### 階段③ 的前置條件：延遲失效觀察期

線上已無舊版節點，且已過觀察期。有些問題在部署當下不會出現，因為**產出物會被帶走**：

- 已發送出去的連結（外部系統可能長期保存或延遲回傳）
- 使用者端已快取的資源
- 已排入佇列、尚未被消費的訊息
- 第三方留存的識別碼或回呼位址

**觀察期以「最後一個舊產出物的有效期限」計算，而非「部署完成時間」。** 輸出時寫出推算依據，例如：連結有效期 7 天 + 第三方最長回報延遲 3 天 → 觀察期 10 天。

---

## 最後一道防線：結果面自動比對

以上流程都依賴人在正確時機想起。唯一不依賴人為判斷的，是結果面的自動監控：持續比對兩個獨立來源的數字（例如原始紀錄與即時計數），落差超過門檻即告警。它檢查的是**結果是否正確**，而非特定錯誤原因，因此能涵蓋所有類型，包含尚未預期到的狀況。

**這類錯誤通常不產生任何錯誤訊息**，只是數字悄悄少了一些；沒有自動比對就只能等人工發現，而損失會隨並行時間持續累積。高風險以上的審核結果，一律要求先具備這層比對再上線。

---

## 何時不要升級為風險

噪音會讓整套流程失去信任，所以下列情況維持「無風險」：

- 只改內部變數名、log 文字、註解、測試
- 已存在的 feature flag 預設關閉且本次不開啟；但若這次同時改了 flag 的讀取或預設值邏輯，它本身就是跨版本契約，回到 Step 1
- 純新增（新欄位、新 endpoint、新 topic），且通過下方三問

### 「純新增」的三個例外

新增不覆寫既有內容，直覺上安全。但以下三種情況它其實就是 Step 1 的共享狀態或跨版本契約：

1. **舊版是否對同一筆記錄做 read-modify-write？** 舊節點讀出整筆、反序列化時丟棄未知欄位、改完整筆寫回，新欄位被抹除。Go 的 `json.Unmarshal` 到 struct、ORM 的整筆 `Save()` 都屬此類；protobuf 保留 unknown fields，JSON struct 不會。這是絕對賦值，依 Step 4 為不可逆。
2. **反序列化是否寬容？** `DisallowUnknownFields`、schema registry 相容性設定、BigQuery／Flink 的 schema 對齊、DB 新增 NOT NULL 欄位而舊版 INSERT 未帶 → 舊節點直接失敗，是服務錯而非資料錯。
3. **新產出物會不會被舊節點消費？** 新 endpoint 在 LB 後方會間歇 404；新 topic 或新訊息型別若消費端未全面上線，訊息會堆積或被舊 consumer 丟棄。處理方式見 Step 5 的部署順序。

三問皆為否才可判定為非風險，並寫出依據（例如「已確認舊版僅以欄位列表更新，不整筆回寫」），而不是只寫「純新增，安全」。

---

## 證據不足時

找不到證據就不要猜，也不要因為不確定而直接判為最高風險——兩者都會讓審核失去參考價值。把它列入「待確認問題」，明確區分**已確認的缺陷**與**需要確認的疑點**。

## 輸出格式

```markdown
## 判定
[可直接漸進式部署 / 需拆階段部署 / 不可直接部署——並行必然造成不可逆損毀]

## 跨版本共用項目（Step 1）
- 共享狀態：<有／無，指到具體檔案或資源>
- 跨版本契約：<...>
- 獨占資源：<...>

## 並行行為對照表（Step 2）
<表格；無法確認的格子標記「待確認」>

## 被刪除邏輯的並行影響（Step 3）
<逐段列出，含「舊節點還會跑多久／期間會做什麼」；無刪除側變更則寫「無」>

## 破壞性等級（Step 4）
<等級 + 依據的寫入方式；不適用則說明原因>

## 建議部署方式（Step 5）
<需拆階段時，列出本次變更中哪些部分屬於 ①②③>

## 延遲失效觀察期
<推算依據；無延遲產出物則寫「無」>

## 上線前必要監控
<結果面比對的兩個具體來源與告警門檻>

## 待確認問題
<必須由提出者回答的清單>
```

判定為「可直接漸進式部署」時輸出可大幅精簡，但仍要寫出 Step 1 三類各自為何為「否」，讓結論可被檢驗，而不是只看到一句「沒問題」。
