# 各語言的文件註解注意事項

只列容易被忽略、會影響判斷的事項。審查時只讀對應語言的區段；沒有對應區段就只用 SKILL.md 的規則。

「風格差異不是缺陷，只有造成可驗證的功能性問題才需要修正」是 SKILL.md 就定調的通用原則，適用所有語言，不是 Go 專屬規則。這裡各語言區段只補充：什麼樣的寫法在**這個語言**裡會踩到那種功能性問題（例如語法被工具誤判、連結失效），以及該語言特有、真正值得寫進文件註解的資訊。不要把「不糾正風格」這件事本身當成每個語言都要各自重申一次的規則。

新增語言時照同樣方向寫：linter 會誘發的無效註解、該語言特有值得寫進文件註解的資訊、屬於 directive 的語法、以及該語言特有會讓工具誤判/失效的寫法。

## Go

- **linter 誘發的翻譯**：`revive`、`stylecheck` 要求 exported 識別字有註解，容易產生 `// Flush flushes the writer.` 這種只重述名稱的註解。改寫成簽章沒說的資訊；真的無話可說時保留最短形式，並考慮是否需要 export。
- **套件文件**：放在 `package` 宣告上方，較長時獨立成 `doc.go`。
- **Go 特有值得寫的**：sentinel error 的語意、context 取消時的行為、呼叫端是否需要 `Close`、零值是否可用、slice / map 參數會不會被保留或修改。
- **directive**：`//nolint`、`//go:generate`、build tags 不是註解。`//nolint` 應附理由，理由適用可信來源條件。
- **縮排會讓連結語法失效**：`[Name]` 建立跨識別字連結時，該行不能被縮排（縮排會被當成程式碼區塊，區塊內的連結語法不會被解析成連結）；`# ` 開頭且獨立成行才會被當成 heading。這是可驗證的功能性錯誤，才需要修正，且只修正縮排本身——不代表要連帶把 `@param:` 這類自訂標籤風格改寫成官方 `# Heading` 語法，那屬於風格選擇，不糾正。

## Python

- **型別提示已表達的不重複**：參數與回傳型別不必再寫進 docstring。
- **模組文件**：放在檔案開頭；套件層級放在 `__init__.py`。
- **Python 特有值得寫的**：raise 的例外與條件、回傳 generator / lazy 物件時的消費限制、pandas / numpy 操作是否 in-place。
- **docstring 風格**：有 Google / NumPy / reST 等多種既有慣例，依 codebase 目前用的那一種判斷一致性即可，不用統一改成特定一種。
- **directive**：`# type: ignore`、`# noqa`、`# pragma: no cover` 應附理由，理由適用可信來源條件。
- **notebook 的 markdown cell**：分析結論（例如「此欄位缺值率 3%」）會隨資料過期。優先改成可重跑的 assertion；無法改時標明資料快照日期與查詢來源。這個日期描述資料版本，git 不會記錄，所以不屬於「應由其他系統記錄」。
