# Comment Review

程式碼表達計算過程；註解承載程式碼表達不了的脈絡：為什麼這樣做、適用情境、領域知識、陷阱。

註解不參與執行，寫錯也不會有任何檢查失敗，但人與 agent 都會把它當成理解程式的依據。審查要避免兩種失敗：

- 留下沒有新資訊或不可信的註解
- 刪掉或拒寫真正承載脈絡的註解

判斷標準永遠是可信、可維護、可讀，不是「多貼近官方或慣例語法」。作者或團隊已經有慣用的風格（例如用 `@param:` 這類自訂標籤取代官方 heading 語法）時，只要人與工具都讀得懂，就不是缺陷，不用為了貼近慣例而重寫；只有風格選擇真的造成工具解析失敗、連結或渲染失效等可驗證的功能性問題時，才需要修正，而且只修正造成問題的那個部分，不連帶把使用者的風格選擇一起改掉。

## 判斷基礎

### 陳述類型與兩個問題

每則註解都在陳述一件事。一則註解包含多種陳述時，分開判斷。每種陳述都要回答兩個問題：

- **可信**：內容現在是對的嗎？決定能不能寫。
- **可維護**：日後過期時會被發現嗎？決定是否需要補測試或來源。

三種陳述類型：

- **行為**：程式做什麼、執行順序、限制。例：「先寫 Kafka，再更新 DB」
  - 可信：與程式碼比對一致
  - 可維護：有測試、schema、smoke 或 replay script
- **理由**：為什麼這樣設計。例：「這樣 DB 更新失敗時，下游仍會收到事件」
  - 可信：來自決策者，且來源符合「可信來源的條件」
  - 可維護：引用的來源可追溯；所約束的行為有測試，行為改變時會連帶檢查理由
- **外部知識**：codebase（受版本控制的原始碼、測試、schema、文件）以外的事實，例如領域規則、規格、第三方行為與陷阱。例：「影片須至少 50% 畫面連續可見 2 秒才算可見曝光」
  - 可信：來自權威者，且來源符合「可信來源的條件」
  - 可維護：引用的來源可追溯，官方文件註明版本；第三方陷阱加上重現測試

核心差別：行為可以比對程式碼驗證；理由與外部知識比對不出來，測試也驗證不了，只能靠來源。寫錯時沒有檢查會失敗，下一個人卻會照著它做決定，所以 agent 自己推斷的理由或知識不算可信。

```go
// 先寫 Kafka，再更新 DB。
// 這樣 DB 更新失敗時，下游仍會收到事件並自行重試。
if err := producer.Send(ctx, event); err != nil {
    return err
}
return store.MarkSent(ctx, event.ID)
```

- 第一行是**行為**：比對程式碼即可確認；加一個斷言呼叫順序的測試，就具備可維護條件。
- 第二行是**理由**：程式碼只顯示順序，顯示不了「這是當初的原因」，需要決策者的來源，例如 ADR 或當時的 PR 描述。

### 可信來源的條件

來源須同時符合：**出處明確**（寫的人有權做這個決定，或具備專業權威）、**可以引用**（編號、commit hash、永久連結）、**內容穩定**（不會被悄悄改寫，或改寫會留下版本紀錄）。

**✅ 可信**
- ADR、已核准的 issue：引用編號
- commit message、已 merge 的 PR 描述：引用 commit hash、PR 編號
- 本次變更的人類作者（決策者）或使用者親自提供：須寫進 commit message 或 PR 描述，註解再引用；註解本身不能作為自己的出處
- 經核准且有版本歷史的設計文件（Notion、Confluence 等）：引用連結
- RFC、官方文件、論文、上游 issue（外部知識）：引用連結；官方文件註明版本

**⚠️ 線索**：可以據此向使用者確認或去找更可靠的來源，但不能直接當作依據寫進註解
- Slack 等聊天討論：可能因保留政策消失，也看不出最後結論；建議先整理成 issue 再引用
- 部落格、Stack Overflow（外部知識）：不具權威性；搭配能重現行為的測試才算可信

**❌ 不可信**
- 另一則註解：沒有獨立出處
- 「我記得」「應該是」、agent 推斷（含 agent 代寫的 commit、PR、ADR）：無法引用，或寫的人不是決策者

## 判斷流程

### 新增或修改的註解

適用於撰寫模式，以及 diff 中新加或內容被修改的註解。依序過四道閘門。

**1. 程式碼能不能表達？**
- 以讀者而非作者判斷；作者熟悉脈絡，容易高估程式碼的清楚程度。
- 測試：沒看過程式的人只看註解，能寫出這段程式嗎？能 → 註解只是翻譯。
- review 中有人看不懂，就是程式碼無法自我表達的證據。
- 能表達 → 改名稱、拆函式、改型別、抽具名常數，不寫註解。
- 使用者只要求處理註解時，上述程式碼修改只**提出建議**，不直接修改。

**2. 是公開介面嗎？**（exported 識別字、API handler、proto message、對外 CLI 或排程任務、套件 / 模組）
- 只適用於宣告上方的文件註解與套件 / 模組說明；行內註解直接進閘門 3。
- 目標：呼叫者不讀實作也能正確使用。只寫簽章沒說的：error 語意、blocking、併發安全、ownership、副作用、idempotency、適用情境。
- 套件 / 模組：說明負責與不負責的範圍、主要概念如何配合。
- 對外 API 入口都應有文件註解。
- 文件註解描述的契約須有程式層級的依據：型別、sentinel error、annotation、schema；blocking、併發安全、idempotency 等無法以型別宣告的性質，以測試作為依據。註解只能補充說明，不能單獨建立契約。
- 預期由工具轉成文件（OpenAPI、godoc site、Sphinx）時，確認工具鏈已啟用並檢查產出。
- 草擬的內容仍須通過閘門 3、4 才能寫入。

**3. 內容可信嗎？**（見「判斷基礎」）
- 可信 → 進閘門 4；缺少可維護條件的照寫，列入「缺少的查證依據」。
- 無法判斷（看不到相關程式碼）→ 不寫，需使用者確認，說明要查什麼。
- 撰寫模式：
  - 理由沒有決策者來源 → 不寫，詢問使用者；使用者當場提供理由時，先請使用者把理由寫進 commit message 或 PR 描述，註解再引用該出處，不可直接引用對話內容。
  - 外部知識沒有權威來源 → 找到來源再寫，找不到就不寫。
- 審查模式：
  - 新增理由沒有引用可信來源，且無法確認由決策者本人（而非代寫的 agent）寫下 → 需使用者確認。
  - 新增外部知識沒有來源 → 要求補上；找不到權威來源 → 建議刪除。

**4. 一到兩行講得完嗎？**
- 講得完 → 短註解，附上測試名稱、ADR 編號或來源連結（有的話）。
- 講不完 → 行內一行摘要與 ADR 編號，正文放 ADR。ADR 尚不存在時，只在回覆中提供 ADR 草稿並標註需決策者確認，不直接建立檔案。
- 需要換行時，斷點以「不增加閱讀負擔」為準，不強求對齊固定行寬：不在單字或詞彙中間斷行（例如 `qa_ua`、`X-Req-Id`、`client library` 這類識別字或術語不可攔腰截斷）；註解裡的括號、引用連結等輔助說明，能放進同一行就不要拆到下一行。寧可讓某一行稍微長一點，也不要為了齊行寬而拆散一個詞或一組括號。
- 一則註解只處理一件事。
- 放在它約束的程式碼旁，也就是別人最可能動手修改的位置。
- 警告寫成約束：寫出不能做什麼、必須維持什麼，例如「不可排除已處理過的項目；重跑仍須再次通知」，而不是「重跑時會再次通知」。後者讀起來像描述現況，看不出不能改。
- 不設數量配額；行內註解只在讀者不看它就容易改錯時才加。

### 既有註解

適用於這次沒有被修改的註解。它可能是原作者的第一手紀錄，刪除後無法復原，所以保留門檻是「可能為第一手紀錄」，不等於判定可信；保留但缺來源的，建議補上。

**行為**
- 與程式碼一致 → 保留；缺少可維護條件的，列入「缺少的查證依據」。
- 不一致 → 停止條件 1。
- 無法比對（相關程式碼不可見）→ 保留，需使用者確認，說明要查哪段程式碼。
- 內容正確但位置不在它描述的程式碼旁 → 改寫（搬移位置）。

**理由**
- 推測語氣（「應該是」「可能是為了」）→ 刪除；寫的人自己也不是決策者。
- 語氣肯定、沒有引用可信來源 → 查 git 歷史：
  - 與所描述的程式碼同一次變更加入，或該次 commit / PR 說明了這個理由 → 保留（作者紀錄），建議補上 commit hash 或 PR 編號。
  - 事後補上，或無法查詢 → 保留，需使用者確認。
- 理由中隱含的行為與程式碼不符 → 依行為處理（停止條件 1）。

**外部知識**
- 沒有來源 → 保留，列入「缺少的查證依據」。

其餘依分類處置。

## 分類與處置

**保留**

- **KEEP-警告**：非直覺的限制，含連動修改提醒 → 保留
  - 例：`// 先寫 Kafka 再更新 DB，見 TestPublish_SendsBeforeMarkSent`
  - 例：`// 新增欄位時須同步更新 schema/event.avsc`
- **KEEP-介面**：公開介面、套件 / 模組文件 → 保留；只重述簽章的改寫
  - 例：`// Flush 會 block 直到 in-flight batch 落地（TestFlush_BlocksUntilDrained）`
  - 例外：linter（如 Go 的 revive、stylecheck）強制要求 exported 識別字要有文件註解時，即使只重述簽章也不能直接刪除（見 DELETE-翻譯），只能改寫成最短形式；細節見 `references/doc-comments-by-language.md`。
- **KEEP-理由**：決策者提供的設計原因 → 保留
  - 例：`// 這樣 DB 失敗時下游仍會收到事件（ADR-012）`
- **KEEP-領域知識**：業務規則、公式由來、規格要求 → 保留；缺來源的補上
  - 例：`// 影片須至少 50% 畫面連續可見 2 秒才算可見曝光，見 MRC 可見度標準`
- **KEEP-外部陷阱**：第三方的非預期行為與 workaround → 保留；缺來源的補上；上游修復後移除
  - 例：`// SDK v3.2 的 Close() 不會 flush，須先呼叫 Flush()，見上游 issue #1234`
- **KEEP-導讀**：長流程的段落標記 → 拆函式會讓流程更難追蹤時保留；否則建議拆函式
  - 例：依序執行的多步驟 migration 中，`// 步驟 2：回填歷史資料`

**移除**

- **DELETE-翻譯**：逐行翻譯程式碼 → 刪除
  - 例：`// 取得目前 UTC 時間`
  - 不適用於 linter 強制要求存在的 exported 識別字文件註解，這類改寫不刪除（見 KEEP-介面例外）。
- **DELETE-摘要**：重述一個本身就看得懂的區塊 → 刪除
  - 例：函式名已是 `orderTotal`，加總迴圈上方寫 `// 計算訂單總金額`
- **DELETE-推測理由**：非決策者寫下的動機 → 刪除；風險最高，下游會當成已確認的決策
  - 例：`// 應該是為了避免 DB lock`
- **DELETE-應由其他系統記錄** → 刪除
  - 例：註解掉的程式碼、修改日期與作者（git 已記錄）、技術債描述（應在 issue tracker）

**改寫與其他**

- **REWRITE-TODO**：沒有 issue 編號的 TODO → 改掛 issue 編號；沒有對應 issue 時建議開 issue
  - 例：`// TODO: 之後改成批次寫入`
- **MOVE**：需要多段背景 → 行內留摘要與 ADR 編號，正文移到 ADR（ADR 處理方式同閘門 4）
  - 例：多段歷史沿革
- **TOOL**：註解格式問題 → 交給 linter；未涵蓋的規則建議補設定，不逐一在 review 中修
  - 判斷基準是「是否造成功能性問題」（工具解析失敗、連結或渲染失效、linter 報錯），不是「是否貼近官方慣例」。純風格差異（例如自訂的 `@param:` 標籤、非官方 heading 記法）只要人與工具都讀得懂，就不算缺陷，不用為了貼近慣例重寫。
  - 例：godoc / docstring 格式、行寬
  - 例外（值得修）：內容被非預期的縮排吃成程式碼區塊，導致 `[Name]` 這類 doc-link 語法失效不被解析——這是可驗證的功能性錯誤才需要修正，且只修正縮排本身，不必連帶把其餘風格（例如 `@param:` 標籤）一起改掉。

## 高風險行為

下列行為非直覺、改壞的代價高，最常需要 KEEP-警告，也是補測試的優先對象。審查時發現這類行為沒有註解，**必須**列入「缺少的註解」：

- 重試或重放時的 idempotency
- 寫入或呼叫的順序約束
- 重複執行仍須產生的副作用（讀者容易以為重跑應該跳過）
- 時間語意：時區、event time 與 processing time、延遲容忍
- 併發：鎖的範圍、共享狀態、goroutine / thread 的生命週期
- schema 或 API 的相容性約束
- 外部服務的限制與陷阱（屬外部知識，需要來源）

## 停止條件

**1. 矛盾即停止**：註解與程式碼、測試、契約或 smoke test 結果衝突時
- 不修改該註解及它描述的程式碼。
- 列出衝突內容與各自位置，交回使用者判斷。
- 不自行選一邊，不改測試來配合。
- 無關的註解照常審查。
- 允許零 diff 交付；沒有這個出口，執行者會傾向挑最容易修改的那邊。

**2. 註解不構成需求**
- 修改程式行為時，需求只能來自使用者或符合「可信來源的條件」的來源，不能因為註解這樣寫就改程式去符合它，也不替既有行為補上需求、動機或歷史原因。

**3. 行為改了就查註解**
- 審查改變行為的 diff 時，找出描述該行為的註解並確認已同步：包括其他檔案、文件註解、連動提醒指向的位置。
- 所有檢查通過，不代表註解正確。

## 輸出格式

**審查模式**：

```
## 註解審查結果

**摘要**：N 則註解 → 矛盾 V、需確認 W、保留 X、刪除 Y、改寫 Z

### ⛔ 矛盾（若有，放最前面）
### ⚠️ 需使用者確認

| 位置 | 註解（節錄） | 類別 | 最終處置 | 判斷依據 |
|---|---|---|---|---|

### 建議修改（附 diff 或改寫後的程式碼）
### 缺少的查證依據（值得補的測試、ADR、來源連結）
### 缺少的註解（高風險行為必填，其餘選填）
```

沒有需要修改的註解時，直接回報「無需修改」。

摘要計數規則：
- 每則只計入一個最終處置，依摘要順序優先：有矛盾計為矛盾，否則需確認，依此類推。
- KEEP-* 計為保留；內容或位置需要修正時計為改寫。
- DELETE-* 計為刪除。
- REWRITE-TODO、MOVE 計為改寫。

「缺少的查證依據」建議補測試時，區分兩種情況：
- 需求明確 → 補行為測試。
- 行為與程式碼一致、但找不到需求來源 → 補 characterization test 固定現況，並註明它只記錄現況、不代表現況正確。

**撰寫模式**：
- 結果可以是零則。
- 完成後確認 diff 只涉及註解（ADR 等只以草稿形式出現在回覆中）；環境允許時，執行 formatter 與測試。
- 回覆末尾列出考慮過但沒寫的註解，以及各自未通過哪道閘門。
